1.1 Addendum — the same day, after this report was written: make.ps1 ran, and failed

Action 6 in §5.1 was completed by the owner within the hour, on a real Windows 11 machine with PowerShell 5.1, and it found a defect no static check in this repository could see:

PS C:\Users\Administrator\Desktop\Git-Clones\DumanMessenger> .\make.ps1 doctor
Cannot validate argument on parameter 'Runtime'. The argument "doctor" does not belong to the set
"auto,wsl,bash" specified by the ValidateSet attribute.

The parameter block declared [Parameter(ValueFromRemainingArguments = $true)] [string[]]$Task with no Position. PowerShell excludes a ValueFromRemainingArguments parameter from positional binding, so the first positional argument bound to the next parameter — $Runtime — and its ValidateSet rejected it. Every documented invocation was affected (.\make.ps1 doctor, ci, help); only the named form -Task doctor worked, and nothing documented it. The script's own .EXAMPLE block, its help text, docs/11 §6, docs/12 and the README quick start all told the reader to type the form that could not work.

Fixed by giving $Task Position = 0 and setting [CmdletBinding(PositionalBinding = $false)] so -Runtime stays a named switch and a second positional argument (--job web --fast) is forwarded to bash instead of being offered to it. check-ps1.py gained a third failure class for this pattern, and it was verified both ways rather than assumed: against the pre-fix file it reports "a ValueFromRemainingArguments parameter has no Position…" and exits 1; against the fixed file it is clean. Five synthetic variants confirm it neither over- nor under-fires — a script with no param block, one with a single positioned pass-through parameter, the corrected two-parameter form, the defective form, and a PowerShell-7 syntax case.

What this does and does not prove. It proves the front door was broken and is now guarded. It does not prove make.ps1 works: that run died at parameter binding, so runtime detection, wslpath translation, the target-to-script table, quoting and exit-code propagation were all still unexercised anywhere. It needed one more transcript from a real machine, and got one within the hour.

1.2 Addendum — the second transcript: the dispatcher worked, and the arithmetic did not

The same machine, minutes later, on ffc2d19:

PS> .\make.ps1 -Task doctor
PS> .\make.ps1 doctor          # both forms now bind correctly
warning: the repo is on the Windows drive (/mnt/...), so WSL file I/O is slow.
bash: line 1: /mnt/c/Users/Administrator/Desktop/Git-Clones/tool/ci/doctor.sh: No such file or directory
error: the wsl runtime exited with 127, which is not a pipeline verdict.

The path in that message is the parent of the clone, which is the whole diagnosis. make.ps1 is committed at the top of the repository — a sibling of Makefile, tool/ and sim/ — so $PSScriptRoot is the repo root, but the script computed Split-Path -Parent $PSScriptRoot under a comment that asserted the opposite ("the repo root is its parent"). That comment is why it survived: it read like a documented fact rather than an untested assumption, and no static check in the repository could see a wrong path three layers away from the arithmetic that produced it.

Fixed to $RepoRoot = $PSScriptRoot, with a startup guard that fails in PowerShell with a reason instead of in bash with a path, and a 127/126 explanation that names the likeliest cause inside WSL (make is not installed by default; the 21 script targets do not need it). check-ps1.py gained a fourth class for the assumption itself, verified both ways and with its boundary pinned: against ffc2d19's make.ps1 placed where tool/ is a sibling it reports the climb and exits 1; against the fixed file it is clean; against the same defective file with no tool/ sibling it says nothing, because there the parent might genuinely be the root.

Two failures on a real machine bought a real verification list, which is worth recording because it is larger than what a static check could ever claim. Now verified by execution on Windows 11 / PowerShell 5.1 / WSL2: parameter binding in both the positional and the named form; WSL2 detection against a real installed distro; wslpath -u translation; the /mnt/c performance warning firing on the right condition; the single-quote-only quoting policy surviving the PowerShell → wsl.exe → bash -lc layers (bash parsed the command and resolved the path, which is the part quoting exists to protect); exit-code propagation; and the defensive branch that refuses to report 127 as a pipeline verdict and says so in terms. Still unverified anywhere: a target completing. No doctor output, no make target and no script target has ever reached a verdict of 0, 1 or 2 through this dispatcher.

Also worth recording: the fifteenth rollback of this branch landed mid-turn, between the two transcripts, resetting local .git to the merge base while the working tree kept every edit. It was repaired with git fetch + git reset --mixed origin/arena/… in one command and cost one verification run (a check that had to be repeated against the right HEAD). 1.3 Addendum — the third transcript was a number, and it closed a release gate

Finding F1 below was written as an owner action because it needed a decision about a wire format. Once CI could run both engines' probe and publish the result, it turned out not to need one: the reference engine's encoding is the minimal one, the divergence was two artefacts of serialisation rather than a design choice, and the arithmetic predicted the fix exactly.

b67c1c7 changed Dart's HistoryEntry.toJson() to omit synced unless it is true (the reference's synced?: boolean is undefined until a copy arrives by repair, and JSON.stringify drops it) and to write an integral at without a decimal point (a Dart double writes 1200.0 where a JS number writes 1200). toJson() has exactly one call site in the engine — the reply body — so nothing else moves, and fromJson already accepted either form. The commit stated the falsifiable prediction: the probe would report 29 750 bytes instead of 30 430. Run 40455143525 reported 29 750, for the same 166 beacons, 3 requests, 2 replies and 171 packets, which is the reference's figure to the byte — and 30 430 − 29 750 = 680 = 17 bytes × 20 entries × 2 replies, the diagnosis confirmed by measurement rather than by inspection.

The gap that allowed it is closed too, not just the instance. Golden vectors v2 carry a history section — the entries, the exact reply body, its length — asserted from both sides: src/__tests__/acceptance.test.ts builds the entries locally and compares JSON.stringify to the fixture, and sim/mesh_sim/test/golden_test.dart rebuilds them through HistoryEntry.fromJson and compares jsonEncode. Neither engine can change its encoding now without moving the fixture, and moving the fixture fails the web job's git diff --quiet gate until both sides are updated in one commit. The run section regenerated byte-identically (avgLatencyMs 526.623, p95LatencyMs 1356.134), which is what docs/06 §17.6's promise is about, and the fixture stays pure ASCII as wire-bytes.test.ts records it must.

4e7b412 closed the last evidence asymmetry: the web job now publishes its vitest tally as a notice, so neither suite's count depends on somebody's memory. It found one bug on the way, in the step itself: the first version grepped for Tests followed by whitespace, and a coloured capture puts an ANSI reset between the label and its count, so it published an empty notice — a silent failure that looks like a published tally. The step now strips escapes first and was verified by executing its own run: text, parsed back out of the YAML, against five capture shapes: coloured, plain, one containing a percent sign (escaped to %25), one with no summary, and a missing file — the last two taking the warning branch rather than publishing nothing at all.

6. Open findings, evidenced but not fixed here

Each of these was found by reading the Dart engine's first-ever output against the TypeScript reference's. None is fixed, and the reason is stated rather than left implied: each needs either a decision about a specified contract or a verification loop this machine does not have.

F1 — RESOLVED in b67c1c7: the two engines disagreed by 680 bytes on what a history repair costs

Identical radio activity, different payload accounting:

Dart   (run 40432981960, probe-history)  166 beacons, 3 requests, 2 replies = 171 packets, 30430 payload bytes
TS     (npm run history, arm 1)          166 beacons, 3 requests, 2 replies = 171 packets, 29750 payload bytes

Localised without running either engine, from the encoders. Both count body.length at the same three sites (beacon, request, reply), and the beacon bodies are identical — 156 characters, 256 B on the wire, printed by both. The request format is the same RQ|group|epoch|buckets|ids string. The difference is in the reply:

  • TypeScript builds it with JSON.stringify(slice) over HistoryEntry objects whose synced?: boolean is optional, so the key is omitted entirely when it was never set.
  • Dart builds it with jsonEncode(slice.map((e) => e.toJson())), and toJson() emits all seven keys unconditionally — including "synced":false, 15 bytes per entry.
  • Dart's at is a double, so an integral timestamp serialises as 123456.0 where TypeScript's number writes 123456: 2 more bytes per entry.

17 bytes × 20 entries × 2 replies = 680 bytes, which is the measured difference exactly. This was first written up as an owner action, on the grounds that choosing a wire format is a decision about a specified contract and not an implementation detail. Reading it back with both engines runnable, that framing was too cautious: docs/06 §17 publishes no byte figure for the reply, the reference engine's form is the minimal one, and the omitted key carries no information the receiver does not set itself. So the Dart encoder was aligned to it, the prediction was stated before the run (29 750 rather than 30 430) and confirmed by it, and the encoding is now pinned from both sides by golden vectors v2. §1.3 has the detail; §5.1 action 3 is closed.
