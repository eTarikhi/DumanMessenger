# ADR: G2-C Android test-only secure BLE link

- **Status:** Transport architecture accepted for TEST-ONLY source; authenticated protocol selection BLOCKED pending owner/security review and API-27 identity-key evidence. No secure session is implemented.
- **Date:** 2026-11-09
- **Scope:** Android-only, TEST-ONLY G2-C link foundation. This ADR does not authorize production messaging integration.

## Context and inspected boundaries

The post-PR-4 app already has API-version-aware Android permission reporting and foreground UUID-filtered BLE discovery/advertising in G2-B. Discovery results deliberately contain temporary session IDs and do not expose device addresses. The Flutter app has separate G2-A diagnostic and G2-B discovery channels. Android crypto in `mobile/app` has no existing mobile identity/session implementation. The repository's `src/crypto` is TypeScript simulator/browser code and is not a suitable native security dependency. The Flutter pubspec has no crypto or BLE dependency. No Android authenticated-handshake library is currently declared or pinned.

## Decisions

### BLE topology and lifecycle

G2-C supports both explicit Android GATT roles: the central/client scans and connects, and the peripheral/server registers the service and advertises. A deployment can choose either role on a given phone; simultaneous client+server role in one manager is rejected to bound concurrent resources. Discovery is an explicit, foreground-only UUID-filtered scan with a 20-second timeout and at most 32 opaque random candidate tokens. The token is not identity; native code retains the device reference only in memory and does not emit its address or name. Connect consumes a selected token (unknown/stale token fails closed). The server starts advertising only after an explicit `startServer`, and the whole G2-C scan/link/server is stopped on Activity pause or bridge disposal.

G2-C primary service UUID: `a71c0001-7d2b-4f5a-9d11-6c47c20a0001`; bidirectional data characteristic UUID: `a71c0002-7d2b-4f5a-9d11-6c47c20a0001`; Client Characteristic Configuration Descriptor is the standard `0x2902`. The characteristic uses write-with-response and notify. Notifications require CCCD subscription; client considers the service ready only after descriptor write completion, server only after valid CCCD subscription. Server accepts one peer at a time and rejects other concurrent peers; teardown clears GATT/server/advertiser references and pending buffers. UUID matching is transport routing only, never identity proof.

MTU starts at mandatory ATT default 23. The client requests 247 after notification setup, but operation does not depend on that request succeeding. Both sides use the negotiated MTU when known and reserve the ATT 3-byte operation overhead. Application fragmentation has a 9-byte fragment header, 2,048-byte maximum reassembled message, at most 192 fragments, one in-flight message per direction, strictly ordered zero-based fragments, full declared-length checks, and a 15-second reassembly deadline. At default ATT MTU 23 this leaves 11 fragment payload bytes and 187 fragments for the maximum message, within the cap. G2-C frame validation has a 4-byte header and at most 512-byte frame payload (516-byte full frame). These limits bound buffers; fragmentation/reassembly is still unauthenticated and never proves peer identity.

All BLE work is user/foreground initiated. Client connection uses `connectGatt(context, false, callback, TRANSPORT_LE)`, available at API 27; server open/service/advertise and scan APIs also predate API 27. Android 12+ checks CONNECT, SCAN, and ADVERTISE runtime grants separately. API 23–30 scan checks legacy ACCESS_FINE_LOCATION; below API 23 runtime grants do not exist. No API 33-only write/notification overload is required. Connection, service registration/discovery, descriptor setup, scan, and assembly have bounded deadlines; disconnect, permission loss, Activity pause, timeout, malformed data, or write failure clear local operations. No background scan/service is introduced.

### Permission request policy (implemented in TEST-ONLY bridge)

The Android app manifest already declares optional BLE hardware, legacy BLUETOOTH/BLUETOOTH_ADMIN capped at API 30, ACCESS_FINE_LOCATION capped at API 30, and Android 12+ BLUETOOTH_SCAN with `neverForLocation`, BLUETOOTH_CONNECT, and BLUETOOTH_ADVERTISE. App Gradle delegates both `targetSdk` and `minSdk` to Flutter (`flutter.targetSdkVersion` / `flutter.minSdkVersion`); this repository does not pin their resolved numeric values, so release/device validation must record them.

G2-C requests only per-operation runtime permissions: scan uses BLUETOOTH_SCAN on API 31+; scan uses foreground ACCESS_FINE_LOCATION on API 23–30; API below 23 has no runtime request. Client connection requests CONNECT on API 31+. GATT server start requests CONNECT and ADVERTISE on API 31+. Legacy connect/advertise permissions are install-time before API 31. The Flutter screen explains the operation before native requests it. Native reports requestable denial vs permanently denied (history plus `shouldShowRequestPermissionRationale`), never proceeds on denial, and offers application settings; returning from settings refreshes actual grants and never auto-restarts radio work. Pending permission dialogs do not leave a scan/server running; an action resumes only when the Activity is foregrounded. This code is source-only and the actual target/API behavior remains unverified.

### Identity and trust

An identity is a public-key byte sequence with a domain-separated SHA-256 fingerprint. A fingerprint is an identifier, not proof that a peer owns its key. Trust is an explicit user confirmation of the full fingerprint through an out-of-band authenticated comparison; scanning/connecting never creates trust. Trust records pin exact public-key bytes, are scoped to G2-C, and support explicit revocation. A different key for an already trusted fingerprint/peer is a replacement attempt and fails closed; rotation requires revoke plus a new explicit trust ceremony. A future authenticated session must bind the exact peer key/fingerprint into its handshake transcript and session object.

#### Required identity/trust lifecycle (designed, not implemented)

1. **Local identity:** Generate a G2-C-only keypair on first explicit setup. Never read or reuse production identity keys. The public-key fingerprint is SHA-256 of a canonical, algorithm-tagged key encoding with a G2-C domain prefix; the existing generic helper is only a raw-byte fingerprint and must be upgraded before use as a security identifier.
2. **Android Keystore:** Keep private identity material non-exportable where the chosen protocol/key type is supported by the device's AndroidKeyStore provider. `KeyGenParameterSpec` is available from API 23, so API 27 has the Android Keystore framework, but the exact key purpose/curve/provider support must be verified on API 27 devices. In particular, do not assume a Keystore key can be used for every static DH operation required by a Noise library. If the chosen protocol needs a key type/purpose unsupported on API 27, do not silently write a plaintext private key or downgrade. Either use an explicitly reviewed Keystore-wrapped encrypted software key with documented in-process exposure, or declare that protocol unsupported on that device.
3. **Peer first contact:** Discovery/advertisement/connection only yields an untrusted candidate. Complete an authenticated protocol handshake that proves possession of the remote static identity key; then show both canonical fingerprints and require an explicit out-of-band comparison/confirmation before changing peer trust to trusted. A service UUID or Bluetooth address is never identity.
4. **Persistence:** Persist only G2-C peer public identity, fingerprint, trust decision/time and format version in app-private storage protected for integrity/confidentiality by a Keystore-managed key. A private key is never stored in plaintext preferences/files. If Keystore access is lost/invalidated, fail closed and require explicit identity reset and re-trust; no plaintext fallback or silent key regeneration.
5. **Revocation/rotation:** Revocation deletes the trusted peer record and invalidates/tears down sessions bound to it. A changed public key at an existing identity/fingerprint is rejected; rotation requires explicit confirmation of the new key and a documented key-transition proof or out-of-band re-trust. Backup/restore must not silently restore stale trust or export private material.
6. **Session binding:** An authenticated session records the exact protocol/version, transcript hash, local and peer canonical public-key fingerprints, role and session-generation identifier. It can be trusted only if the authenticated handshake succeeds and the peer's key is explicitly trusted. New connection, rekey, timeout, disconnect, app pause, key change or revocation invalidates the prior session.
7. **Unknown peers:** A peer without a valid protocol identity proof and explicit current trust record remains unknown/untrusted; payload delivery is rejected. No trust-on-first-use or automatic trust is allowed.

Keep these as distinct state axes: **discovered** (temporary radio candidate), **connected** (GATT link), **service ready** (expected GATT schema/CCCD ready), **authenticated** (cryptographic peer proof and session established), **trusted** (user-approved pinned identity), and **disconnected**. The current Flutter/native source implements only the first three transport stages; `authenticated` and `trusted` are not produced by code. The existing process-local key pin abstraction is not durable or connected to the transport.

### Cryptographic protocol

Do not implement a bespoke handshake. No suitable vetted Android protocol dependency is present in the inspected app. Existing TypeScript Noise-like code is not accepted as a native implementation or dependency.

No cryptographic dependency was present in the Flutter or Android dependency declarations at baseline, and no candidate has been added. Candidate tradeoffs and blockers:

| Candidate | Potential fit | Current blocker / security condition |
|---|---|---|
| Maintained Noise Protocol Framework implementation for JVM/Android | Stream-friendly, explicit handshake patterns and transcript/prologue support can fit BLE records. | No specific artifact/version selected or independently verified. Must establish API 27 compatibility, Java/Kotlin support, license, maintenance/release history, protocol pattern semantics, test vectors, and identity-key integration. A primitive-only Noise implementation is not enough without correct static identity validation. |
| Android Tink | Maintained vetted primitives and key-management APIs can reduce primitive misuse. | It is not a complete authenticated BLE handshake protocol; composing ECDH, signatures, transcript binding, role binding, KDF, AEAD, replay handling, and teardown at app level would create a custom protocol. Not accepted as a shortcut. API 27 and exact version/dependency compatibility still require evidence. |
| Mutual-authenticated TLS over a BLE byte-stream adaptation | Mature record protocol, identity certificates, transcript integrity, and sequence handling. | TLS 1.3 platform availability is not guaranteed on API 27; certificate identity/pinning UX and adapting a record layer to bounded GATT writes/notifications adds substantial complexity. No platform TLS profile was verified for the full API 27 matrix. |
| Hand-rolled JCA ECDH/signature/HKDF/AEAD | Available platform crypto APIs. | Rejected: primitives do not supply protocol composition, downgrade resistance, transcript semantics, peer authentication, or robust replay/session lifecycle. |

#### Source evidence inspected (GitHub API, 2026-11-09)

- [Noise Protocol Framework specification repository](https://github.com/noiseprotocol/noise_spec) identifies revision 34 (`v34`, published 2018-07-11) in the inspected repository metadata. The framework is a specification, not a JVM/Android implementation or release guarantee.
- [rweather/noise-java](https://github.com/rweather/noise-java): repository metadata reports MIT, no GitHub releases or tags, last push 2024-03-28; its checked-in Maven POM says `1.0-SNAPSHOT`, compiler source/target 1.8. Its README calls it a plain-Java reference implementation using JCE and Java fallbacks. This is encouraging language/API compatibility evidence, but not evidence of API 27 provider behavior, current maintenance, published artifact provenance, complete review, or an independent audit.
- [jchambers/java-noise](https://github.com/jchambers/java-noise): repository metadata reports MIT, no releases or tags, last push 2025-04-02; its POM targets Java 17. The README states it is not yet published to an artifact repository and has not received an independent security audit. It requires provider support for X25519/X448 and ChaCha20-Poly1305 when those algorithms are selected. Therefore it is not selected for an API-27 Android app on available evidence.
- [tink-crypto/tink-java](https://github.com/tink-crypto/tink-java): repository metadata reports Apache-2.0, active repository, release `v1.24.0` dated 2026-10-16 (latest release observed), and an Android example whose Gradle file sets `minSdkVersion 23`. This is source evidence that its example targets below API 27; it does not establish that Tink is a complete mutual authenticated key-exchange/session protocol. Tink offers reviewed primitives/building blocks, but assembling identity authentication, transcript, roles, replay, rekey and teardown in this app would be custom protocol composition and is not approved.
- Platform TLS (`SSLEngine`/Conscrypt) remains a candidate only in principle. No API-27 mutual-TLS profile, BLE record framing, certificate UX, or identity-pinning interoperability evidence was verified in this inspection. TLS 1.3 availability on the full minimum-API matrix is specifically unresolved.

These are repository-source/metadata observations, not a security audit, vulnerability review, compatibility test, or dependency approval. Repository push timestamps/releases do not by themselves establish adequate maintenance or independent review. The outbound-host restrictions and prohibition on builds mean no Maven artifact was downloaded/resolved and no API-27 compile/runtime test was performed.

Therefore **no cryptographic library or protocol is selected**. Before implementation, the owner and independent security reviewer must choose a concrete protocol and pinned artifact/source commit, review known advisories and provenance, verify API 27 key/provider behavior, licensing and transitive dependencies, run protocol vectors/interoperability, and approve the identity/trust, downgrade, transcript, session, replay, rekey and teardown design. No unauthenticated ECDH, fingerprint-only exchange, fallback, or BLE link-encryption substitution is allowed. The ADR deliberately provides no session keys or authenticated status.

### Protocol/data boundary

The current version-1 frame and fragment codecs perform strict bounds/order/length validation and reject malformed, duplicated, out-of-order, truncated, or expired reassembly. They have no cryptographic authentication, direction/session binding, or replay protection. Test frames are accepted only at the isolated G2-C transport callback, which currently discards them rather than forwarding to any application or production messaging. This is transport plumbing only, not a secure data plane.

## Alternatives rejected

- Trust-on-first-discovery: rejected; Bluetooth addresses and service UUIDs are unauthenticated and can be spoofed.
- Treat Android BLE pairing/link encryption as E2E: rejected; it does not establish Duman peer identity or provide application-level identity/session binding.
- Reuse `src/crypto` or production identity/state: rejected; wrong runtime/boundary and unjustified cross-scope key reuse.
- Hand-roll ECDH/signature/HKDF/AEAD handshake: rejected; protocol composition and downgrade/replay defenses require an established reviewed protocol.
- Silent unauthenticated fallback: rejected; no secure-session state is exposed until handshake verification exists.

## Assumptions and limitations

Physical devices must support BLE GATT roles; peripheral capability is not universal. Android 8.1/API 27 lacks modern runtime Bluetooth permissions, but still requires legacy location permission for scanning under the existing manifest. Android 12+ permissions are explicit. Bluetooth transport and radio conditions are untrusted. This ADR does not establish production readiness, privacy guarantees for radio metadata, or resistance to compromised endpoints. No builds/tests/device checks have run.

## Phase 4 source-audit record (source inspection only)

The G2-C client/server/discovery, Flutter bridge/screen, MainActivity integration, manifest declarations and permission state mapping were re-read without running builds or runtime validation. The client retains callback identity/state gates and pending descriptor/write guards. Source inspection found two server-side idempotence/classification defects in the existing G2-C scope: duplicate `onNotificationSent` callbacks could advance a second fragment, and duplicate connected/service-added callbacks could reset connection progress or restart advertising. A pending-notification-index guard and service/peer duplicate guards were added. Generic “unavailable” operation errors also incorrectly mapped Bluetooth-disabled state to unsupported; the mapping now distinguishes `bluetooth_unavailable` from actual unsupported capability. These are source-level corrections only, not proof of platform callback ordering or notification delivery.

The Flutter screen uses actual native events and operation calls, displays opaque candidates and typed states, rejects an authenticated native status, and disposes its event stream and operations. API 27 source uses legacy Bluetooth permissions plus foreground ACCESS_FINE_LOCATION for scanning; modern Android permission requests are operation-specific. App Gradle still delegates min/target SDK to Flutter defaults, and API 27 provider/platform behavior remains unverified. The server callback is still shared across GATT-server lifecycles; stale callbacks across a rapid stop/restart cannot be excluded by source inspection alone and must be specifically observed on owner devices. GATT and permission behaviors are not compiled or runtime-validated.

No code establishes identity, trust, a secure session, replay protection, or a production data path. The raw-byte identity helper is not canonical protocol identity, the trust seam is process-local and disconnected from GATT, and no private key lifecycle exists. No production key reuse or plaintext private-key fallback is added.

### Exact evidence still required before protocol work

- A pinned dependency coordinate/version or immutable source commit, artifact provenance and transitive dependency inventory; current Noise Java coordinates/releases are not verified and the Tink Android artifact coordinate was not resolved.
- License and maintenance/advisory review for the exact artifact, not just repository-level metadata.
- API 27 Android provider support for required key types, purposes and operations; Kotlin/JVM packaging plus tested vectors/interoperability on the minimum-API matrix.
- A selected protocol pattern/profile with explicit mutual authentication, canonical identity binding, transcript/role/downgrade binding, replay defense, session key derivation, rekey/expiry/teardown semantics and certificate/trust UX as applicable.
- Independent security review evidence and written owner/security approval of the complete protocol and key lifecycle. No custom handshake or dependency addition is authorized before these gates.

## Consequences and next decisions

Phase 2 source provides G2-C client/server and filtered discovery, foreground cleanup, GATT service/CCCD setup, and bounded bidirectional fragmentation. Phase 3 adds a focused TEST-ONLY Flutter control screen and operation-scoped Android permission requests/settings remediation. Phase 4 records a source-only audit and Windows owner handover guide. These changes have not been compiled or runtime-tested. Protocol selection remains BLOCKED, and the identity/trust lifecycle above is a design only. Authenticated sessions, persistent key/trust, replay protection, secure data plane, negative tests, independent security review, owner Windows validation, and two-device acceptance remain future gates. Never describe this foundation as secure communication.
