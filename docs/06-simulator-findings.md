# 06 — Simulator: implementation findings & calibration evidence

> Companion to `skills/08-qa-simulator.skill.md`. Records *why* the simulator is
> calibrated the way it is, what the measurements say, and which documented
> target is not yet met. Everything here is reproducible from CI.

**Status:** engine implemented in two languages and executed in CI; every
`skills/02` + `skills/08` simulator criterion met on the 20-node case they name,
at **7-9%** of the naive-flood relay budget (§2). Power policy, the duty cycle and
the Phase 2 telemetry are implemented and measured (§10) — the duty cycle is what
brings NORMAL inside `skills/07`'s 15%-per-8h budget. SOS mode (roadmap Phase 3),
hop transparency (roadmap Phase 4) and group channels (roadmap Phase 1) are
implemented and measured (§11, §13, §14), and a protocol defect both engines
shared — a node re-flooding copies of its own message — was found by a render test
and removed (§12), cutting relay transmissions 18.3% in the warm 20-node world.
The documented 10-200 node range is now measured end to end, which found a
quadratic cliff at the top of it and fixed it (§15). One secondary target remains
open in the 60-node crowd (§6) — §16 decomposes that tail message by message,
measures the two levers that were supposed to close it, and records why neither
does: faster beacons make it worse, and more retries buy delivery rather than hop
count.
**Date:** Oct 2026

## 1. What exists

| Path | Role |
| --- | --- |
| `sim/mesh_sim/` | **Authoritative Dart engine** (`duman_mesh_sim`). Headless, pure `dart:core` + `dart:math`, no Flutter dependency, so it runs in CI and can be dropped into the app's `test/` harness later. CLI: `dart run bin/mesh_sim.dart --scenario campus_quad --seed 42`. |
| `src/` | **TypeScript reference engine + React visualiser.** Same algorithms, same constants, same RNG draw order. `npm run dev` for the canvas, `npm test` for the suites. |
| `test-fixtures/golden-vectors.json` | Cross-language contract. Generated by `npm run golden`; asserted by both `src/__tests__/acceptance.test.ts` and `sim/mesh_sim/test/golden_test.dart`. CI fails if it is stale. |

Both engines are discrete-event simulations on a **virtual millisecond clock**.
Nothing touches wall-clock time or an unseeded random source, so a seed
reproduces a run exactly — which is what makes the numbers below meaningful.

## 2. Acceptance criteria and where they come from

- `skills/02` — *"Simulator 20 nodes: SUPER ratio 15-25%, delivery ≥90% at 3 hops, overhead ≤70% of flood-all."*
- `skills/08` — *"CI simulator: 20-node seed → delivery ≥90% <5 hops, overhead ↓30% vs naive flood."*
- `docs/04` §5 — latency budget *"1 hop < 2 s; 3 hops < 5 s"*.
- `docs/03` §5 — *"hysteresis: prevent SUPER flapping."*

`delivery ≥90% <5 hops` is read as: **at least 90% of sent messages arrive
within five radio hops**. ACKs and broadcasts are excluded from the ratio so
control traffic cannot inflate it.

Three arms run per configuration — same seed, same world, same traffic plan
(§7). `mpr` is what ships; `route-flood` keeps routing and switches suppression
off; `flood-all` is naive epidemic flooding, no route table and no suppression,
which is the baseline both criteria name.

## 3. Radio calibration

`rssi(d) = txPowerDbm − 20·log10(d) − wallCrossings · wallPenaltyDb` (docs/05 §1.1, skills/08).

The prototype this replaced used `txPower = −30 dBm` over an 800×600 canvas with
radius-100 UI circles. That combination yields a **562 m radio** — inside the
documented 100×100 m test area every node hears every other node, yet the
prototype still reported 11–18 of 20 nodes isolated, because the two numbers
were never consistent with each other. The calibrated model:

| Parameter | Value | Effect |
| --- | ---: | --- |
| `txPowerDbm` | −55 | 1 m reference |
| `rxSensitivityDbm` | −85 | ⇒ **31.6 m** line-of-sight hop |
| `wallPenaltyDb` | 12 | one interior wall ⇒ ~18 m |

31.6 m sits inside the documented "BLE 10–30 m indoors" budget, and 3–5 SUPERs
in a 100×100 m quad is exactly "at most 1 SUPER per ~30 m radius" (π·30² ≈ 2800 m²,
10 000/2800 ≈ 3.5).

### Packet loss needed two corrections

1. **Margin, not normalised RSSI.** `(1 − normRssi)²` made a 10 m link 41% lossy
   and collapsed delivery to ~35%. Loss is now driven by margin above receiver
   sensitivity: `margin = clamp(rssi − rxSens, 0, 30)`, `raw = 0.45·(1 − margin/30)²`.
   Measured raw loss: 2 m 1.8% · 10 m 20% · 20 m 34% · 30 m 44%.
2. **Link-layer retransmission.** BLE GATT writes and Wi-Fi Direct sockets are
   *reliable* bearers; the link layer retries before a failure is reported
   upwards. App-visible loss is therefore `raw^(linkRetries+1)` with
   `linkRetries = 2`: 20 m 34% → **3.9%**, 30 m 44% → **8.3%**.

Lossy links are what make the PDR term of the coverage score meaningful — a node
whose neighbours keep dropping packets should not be elected SUPER.

## 4. Protocol corrections found while measuring

These are behaviour fixes, not tuning knobs. Each is pinned by a test.

1. **Stale routes were immortal.** Nodes advertised second-hand `bestHopTo`
   entries in their own beacons, and receiving a beacon re-stamped `lastSeen`.
   A dead destination therefore never aged out: prune deleted it, a neighbour
   re-advertised it, it was recreated with a fresh timestamp. `bestHopTo` now
   only *bootstraps* an entry that does not exist, and `buildOGM` only
   advertises routes backed by direct evidence (`lastSeq > 0`). Fixing this cut
   the reference run's relay count from 719 → **507** and p95 latency from
   1409 → **1055 ms**.
2. **`uptimeMin` started at 0–30 min.** The documented stability term is
   `min(uptimeMin/60, 1) · (1 − mobility)`, so in a 4-minute run it could never
   saturate and silently starved the coverage score. A real handset has been up
   for hours: it now starts at 30–360 min. Delivery went 87% → **93%**.
3. **No source retransmission.** docs/03 §6 has the destination ACK "via reverse
   path", but nothing acted on a missing ACK. The originator now retransmits
   after `ackTimeoutMs` (4 s) up to `maxRetries` (2), then falls back to the
   OppQueue. Retries carry the same logical `id` with a new `attempt`, and
   intermediate nodes dedup on `id#attempt` — otherwise the retry would be
   swallowed by the nodes that already relayed attempt 0.
4. **Spray-and-Wait dropped the bundle at the limit.** docs/03 §8 says
   *"if copyCount == 3: keep but lower priority"*. The bundle is now retained
   (so it can still be handed straight to the destination) and demoted to
   `priority: low`.
5. **The SUPER proximity guard was inert.** docs/03 §5 pairs "~30 m radius" with
   "RSSI > −60", which only agrees for the doc's original tx-power assumption.
   At −55 dBm, −60 dBm means **3 m**, so the guard never fired. The threshold is
   now derived from the RF parameters (`tx − 20·log10(30)`), preserving the
   documented *physical* meaning.
6. **Uniform spawning ignored buildings.** Nodes could spawn inside an obstacle
   and stay there forever (one seed produced a node with 0 peers and 5 of 20
   nodes unreachable). Spawn points are now rejection-sampled (≤16 redraws) and
   clamped to the area.
7. **Waypoint mobility, not a random walk.** A pure random walk at 1.4 m/s moves
   a node up to 250 m in a 225 s run — people left their cluster and isolated
   themselves. `skills/08` asks for "random walk **+ waypoint clusters**": nodes
   now walk to a waypoint near their home position and renew it on arrival or on
   a 5% roll, so a crowd stays a crowd. This alone took `campus_quad` from
   19/20 to **20/20 connected** on every seed.

## 5. MPR suppression had to be gated on coverage

> The figures in this section were measured before the tq defect in §6 was
> found, and its `flood-all` arm still consulted the route table, so it was not
> the naive baseline the criteria name — "delivery parity with flooding" below
> means parity with *routing without suppression*, which is the arm §7 now calls
> `route-flood`. The comparison it draws — coverage-gated suppression against the
> doc-literal "heard a SUPER" rule — still holds; the absolute numbers are
> superseded by §2.

The first working version implemented docs/03 §6 literally — *"wait 300 ms; if no
retransmit from SUPER heard: forward"* — and in the 20-node quad it looked fine.
At 60 nodes it did not:

| policy | delivery (2 seeds) | relay transmissions | suppression |
| --- | ---: | ---: | ---: |
| MPR, "heard a SUPER" | 78.7% / 66.7% | 23 248 / 16 869 | 1772 / 1482 |
| flood-all | 94.7% / 95.3% | 72 134 / 80 282 | — |

Cutting relays by 68-79% while losing **16-29 points of delivery** is not the
trade docs/05 §"Duman's hybrid selection" promises ("reduces redundant
transmissions by ~30% vs naive flood" — with the same delivery).

The cause is structural. Hearing a SUPER retransmit says nothing about whether
that SUPER reaches *this node's* neighbours. A SUPER three clusters away still
silenced a node whose own neighbours heard nothing, and the hole showed up as a
lost message. docs/01 and docs/03 §1 both define MPR correctly — a relay set
**"covering 2-hop neighbors"** — so the fix is to gate suppression on coverage:

> Stay quiet only when the neighbours this node actually heard the message from,
> plus their advertised neighbour lists, cover **all** of its own 1-hop
> neighbours. Otherwise forward.

That needs the 2-hop view, which needs the OGM to carry the originator's own
neighbour list (OLSR's HELLO payload) — a field docs/03 §4's OGM definition
omits. It is now `neighborIds`, capped at 30.

**The cap is load-bearing.** The first attempt capped it at 12. A 60-node crowd
has 15-18 peers per node, so every advertisement was truncated, full coverage
became arithmetically impossible, suppression collapsed from 1772 to **110**, and
overhead went *up* to 92-104% of flood-all. Raising the cap to 30 (the `k ≤ 30`
local-sort budget docs/03 §4 already sets) restored it.

A second refinement mattered just as much: a neighbour we received a copy *from*
already holds the message, so it never needs covering. Counting those senders
(not just relays that retransmitted at hopCount ≥ 1) took `campus_quad` overhead
from 58-73% to **54-68%** with no delivery cost.

### After

| scenario | policy | delivery | relays | overhead vs flood-all | suppression |
| --- | --- | ---: | ---: | ---: | ---: |
| campus_quad (6 seeds) | MPR | 98.7-100% | 5 251-7 682 | **54-68%** | 450-711 |
| campus_quad (6 seeds) | flood-all | 99.3-100% | 9 105-13 210 | — | 0 |
| festival_crowd seed 42 | MPR | **88.7%** | 40 476 | **54%** | 2435 |
| festival_crowd seed 42 | flood-all | 87.3% | 75 557 | — | 0 |
| festival_crowd seed 7 | MPR | **89.3%** | 36 545 | **50%** | 2028 |
| festival_crowd seed 7 | flood-all | 93.3% | 72 536 | — | 0 |
| festival_crowd seed 1234 | MPR | **93.3%** | 44 302 | **54%** | 2280 |
| festival_crowd seed 1234 | flood-all | 92.7% | 81 807 | — | 0 |

MPR now reaches **delivery parity with flooding at roughly half the relay
budget** — 46-50% fewer transmissions in the crowd, 32-46% in the quad, against
the 30% the docs require. `acceptance.test.ts` asserts the parity directly
(`delivery ≥ floodDelivery − 0.05` and `overhead ≤ 0.70`) so a regression in
either direction fails CI.

## 6. Link tq was measured per route, not per link

Chasing the crowd's 5-hop shortfall turned up a defect in the control plane that
had nothing to do with density.

docs/03 §7 defines `tq = (OGMs received via that neighbor / OGMs expected)` over a
window of 32 — a **link** metric. The implementation kept one window per *route
entry*, tagged with the neighbour that had last won it. A copy of the same beacon
arriving over a different neighbour is not newer, so it recorded no sample — but
it did discard the window, because that window belonged to somebody else, and tq
fell to 0:

```
seq=5 hop=0 via=node-6  newer=true   window 1/1  tq=1.0   <- perfect direct link
seq=5 hop=3 via=node-2  newer=false  window RESET tq=0.0   <- gossiped duplicate
seq=5 hop=4 via=node-3  newer=false  window RESET tq=0.0
```

Gossiped duplicates always land after the direct copy, so **zero was the steady
state**:

| | mean tq, direct neighbours | usable routes (`tq ≥ 0.6`) |
| --- | ---: | ---: |
| `campus_quad` before | **0.107** | 29.7% |
| `campus_quad` after | 0.935 | **86.8%** |
| `festival_crowd` before | **0.061** | 46.6% |
| `festival_crowd` after | 0.934 | **91.8%** |

Three consequences, none of them visible in the aggregate metrics:

1. `getNextHop` gates on `tq > 0.6`, so almost every route was rejected and the
   network flooded blindly. Multi-hop unicast — the point of the BATMAN-lite
   control plane — essentially never happened.
2. `buildOGM` advertises only entries with `tq ≥ 0.6 && lastSeq > 0`, so nodes
   told each other almost nothing and route discovery could not bootstrap.
3. The window never grew past one sample, so the 32-interval average the spec
   asks for was never computed. Second-hand entries six hops away read
   `tq ≈ 0.99` — an artefact of the same reset, since a freshly created window
   holds exactly one optimistic sample.

**Fix.** tq is kept per `(originator, neighbour)` pair in `node.tqWindows`,
bounded by `TQ_PAIR_MAX = 2048` with insertion-order eviction (stable in both JS
Maps and Dart LinkedHashMaps, so the two engines evict identically) and pruned
when a neighbour stops being a peer. A route entry reports the window of the
neighbour it actually routes through, whichever copy arrived last. The
"if seq newer" rule now applies *per pair*: a copy that is stale globally can
still be fresh for a neighbour we have not heard it from.

**Effect on the reference run** (golden vectors — `campus_quad`, seed 42, 20
messages): delivery 18/20 → **20/20**, relays 383 → **253**, p95 latency
1363 → **950 ms**. In the crowd: delivery 88.7-93.3% → **91.3-95.3%**,
within-5-hops 80-85% → **82.7-89.3%**.

### The baseline this exposed

With routing broken in *both* arms, "overhead vs `flood-all`" accidentally meant
what it said — MPR versus blind flooding. Once routing worked, the `flood-all`
arm began using the route table too, and the campus overhead ratio climbed to
71-78%: the baseline had got better, not the engine worse. `flood-all` is now
naive by construction — consulted before the route table — and `route-flood`
exists so MPR's marginal contribution can be quoted separately. Both columns are
in §2, because quoting only the 7-9% would hide that most of it is routing.

### Still open

In the 60-node crowd **82.7-89.3%** of sent messages arrive within five hops
(average 2.6-3.0, p95 4.8-6.4 s), against 97.3-100% in the 20-node case the
criteria actually name. The tail is 9-12 messages arriving at exactly six hops —
the ceiling a data `ttl` of 5 allows — plus 7-11 that expire.

**§16 takes this apart and closes the investigation.** Over six seeds the figure is
84.1%, and the tail decomposes into 2.2% geometric (BFS distance ≥ 6 at send time),
1.8% with no path at all, 5.8% lost or expired and 5.8% delivered with more hops than
the send-time shortest path — the last of those being the world moving while the
message was in flight, since some messages arrive in *fewer* hops than BFS said were
possible. Neither obvious lever closes it: halving the OGM interval costs 1.95× the
control traffic and *loses* 1.1 points, and doubling retries buys 1.5 points of
delivery for 62% more p95 latency and no hop-count gain. The defaults stay where they
are, and the honest claim is the decomposition rather than a tuning change.

The obvious candidate, raising `ogmTtl` so route discovery sees further, is
**falsified by measurement**:

| `ogmTtl` | crowd ≤5 hops (seeds 42 / 7) | OGM transmissions | second-hand entries |
| ---: | ---: | ---: | ---: |
| 5 | 127 / 134 | 813 k / 785 k | 25% / 20% |
| 7 | 123 / 134 | 1 127 k / 1 130 k | 11% / 19% |
| 10 | 127 / 138 | 1 632 k / 1 644 k | 13% / 5% |

Deeper gossip does replace second-hand routes with direct evidence, and it buys
nothing: ±2 points of within-5-hops, which is noise, for **2× the control
traffic**. The residual is geometric, not informational — the crowd's clusters
are 61-74 m apart against a 31.6 m hop, so three hops is the *floor*; 80% of
nodes are moving; and a 16×12 m "Sound tent" sits on the direct line between two
of the clusters. Holding a 140 m, 60-node field to a five-hop budget needs either
a longer data TTL — which converts undelivered messages into 6-7 hop ones and so
*lowers* the ratio — or a density this scenario deliberately does not have.

## 7. Methodology note on the A/B

The overhead figure compares MPR against `flood-all` **on the same seed and the
same traffic plan**. Drawing message pairs from the simulation's own RNG does not
work: the 300 ms MPR wait changes event interleaving, so the two arms consume the
RNG stream differently and quietly become two different experiments. Early runs
produced "overhead" of 119% and 155% — MPR apparently worse than flooding — which
was pure artefact. Both engines now pre-generate the pair list from a separate
seeded generator and replay it into every arm.

The same logic applies to what the arms *are*. Three run per configuration:

| arm | routing | MPR suppression | answers |
| --- | --- | --- | --- |
| `mpr` | yes | yes | what ships |
| `route-flood` | yes | no | what MPR costs and buys, holding routing fixed |
| `flood-all` | no | no | the documented "naive flood" baseline |

Two rules follow, both learned the hard way (§6). A baseline must not silently
share the mechanism under test — `flood-all` consulting the route table made the
overhead ratio meaningless the moment routing started working. And a suppression
mechanism must be judged against the arm that differs from it by suppression
only: naive epidemic flooding reaches 100% delivery in the crowd by spending 7-9×
the relays, so "within 5 points of flood-all" is not a test of MPR, it is a
demand for epidemic redundancy. That comparison is also made on the **mean across
seeds**, because 150 messages through a chaotic 60-node world carries several
points of run-to-run variance that a per-seed bound would mistake for a
regression.

## 8. Reproducing

```bash
npm ci && npm test                 # TS engine: 117 tests incl. acceptance + golden
npm run golden                     # regenerate the cross-language fixture
cd sim/mesh_sim && dart pub get && dart test
dart run bin/mesh_sim.dart --scenario campus_quad --seed 42 --json
dart run bin/mesh_sim.dart --policy route-flood --scenario festival_crowd --no-check
```

`--policy` picks the arm under test (`mpr` | `route-flood` | `flood-all`). The CLI
replays the same plan through the other two as well and reports
`overheadVsFloodAll` and `overheadVsRouteFlood`, so a single invocation
reproduces both overhead columns in §2.

`bin/mesh_sim.dart` exits non-zero when the acceptance criteria fail, so CI can
gate on the CLI directly. Scenarios: `campus_quad` (the 20-node acceptance case),
`sparse_village` and `partitioned_pair` (DTN / store-carry-forward), and
`festival_crowd` (the docs/02 §6 "50+ nodes" density target).

> The DTN scenarios are *deliberately* partitioned — their low immediate
> delivery ratio is the point. They are reported with `--no-check` and asserted
> on queue depth instead, because a 24% delivery ratio with 112 bundles carried
> is a healthy delay-tolerant network, not a broken one.

## 9. Porting notes (TypeScript ⇄ Dart)

The two engines are kept mechanically equivalent so a golden-vector mismatch
means real drift:

- **RNG.** mulberry32 in unsigned 32-bit space. Dart ints are 64-bit, so every
  intermediate is masked with `0xFFFFFFFF`; that reproduces JavaScript's
  signed-32 bitwise semantics bit-for-bit, and `Math.imul` becomes a masked
  multiply (`_imul`). **Both operands of each multiply must be read from the same
  `t`.** The first port overwrote `t` with the XOR result first, computing
  `(t ^ t>>15) * ((t ^ t>>15) | 1)` instead of `(t ^ t>>15) * (t | 1)`. That is
  still a plausible uniform stream — it just is not mulberry32, and the first
  draw for seed 42 came out 0.443627356 instead of 0.601103752. Nothing local
  caught it; only a second implementation forced to reproduce the same numbers
  did.
- **Integer literals in a double context.** Dart folds integer *constant
  expressions* to double (`const double oppTtlMs = 7 * 24 * 60 * 60 * 1000` is
  legal), but an expression over a variable is not: `scanOppQueue(..., 1000 + i)`
  is an `int` and will not bind to a `double` parameter. Write `1000.0 + i`.
- **New node fields must be derived, never drawn.** `dutyPhaseMs` (§10) is
  computed from the node index, not read from the RNG, because any extra draw
  shifts every value after it and invalidates the goldens in both languages at
  once.
- **Draw order is a contract.** Node construction draws in a fixed order
  (`name → stationary → charging → position → battery → uptime → wander → pdr →
  heading → target`), and the rejection-sampling loop redraws in the same order.
  Changing it invalidates the golden vectors in both languages.
- **`log10`.** `dart:math` has no `log10`, so the Dart engine uses
  `log(x)/ln(10)`. That can differ from `Math.log10` in the last ULP, so golden
  comparisons are tiered: RNG values and protocol counters must match **exactly**;
  float aggregates use a tolerance; spawn geometry uses 1e-6.
- **`destHint`.** Both engines use the same 32-bit string hash
  (`h = h*31 + charCode`, truncated to 8 hex chars) so routing hints agree.

## 10. Power policy: the sleep slot is what makes the battery budget work

`skills/02`'s battery line (*"SUPER opt-out respected; NORMAL never auto-promoted
if battery saver on"*), `skills/07`'s duty cycle and telemetry rows, and the
roadmap's Phase 2 *"metrics dashboard: delivery ratio, overhead ratio, latency by
hop, battery %/h"* were the last unchecked items the simulator could settle. All
are now implemented in both engines, **off by default, goldens byte-identical** —
every new field is either derived or a config knob, so the RNG draw order that
`test-fixtures/golden-vectors.json` pins is untouched.

### 10.1 The two gates do not wait for hysteresis

`electRole` checks `superOptOut` and `batterySaver` **before** the peer and
battery gates and returns NORMAL immediately, clearing `demoteCounter`. docs/03
§3's two-cycle demotion rule exists to damp *score* noise; a user flipping a
switch is not noise, so making it wait 60 s would be a bug wearing the clothes of
consistency. `docs/03` §3 already listed "Not in battery saver" as an
eligibility gate — this implements it. Both switches are user-visible in the
simulator's node inspector (`setSuperOptOut` / `setBatterySaver` re-elect on the
spot).

### 10.2 A declined node has to be advertised, or it eats a candidacy slot

The first cut gated only the node itself. Opting out a third of a 20-node mesh
(`campus_quad`, seed 42) then left **2 SUPERs (ratio 0.10)** — below the 15%
floor the same skill file demands — because §4 step 3's top-20% ranking still
counted the declined nodes as candidates. Each one occupied a slot it could never
fill, and the mesh got a coverage hole for free.

The OGM therefore carries **`declinedRouter`** (1 bit: opt-out or battery saver,
preserved through `copyWith` so a gossiped copy does not lose it), and peers drop
declined originators from the ranking set. Same run after the fix: **4 SUPERs
(ratio 0.20)**, delivery 100% over 30 messages at 1.57 average hops. A device
cannot read its peers' local settings, so this had to be broadcast rather than
inferred — the same argument §4 already makes for `neighborIds`.

### 10.3 Measured battery burn: the budget has zero headroom until a node sleeps

`skills/07` sets the acceptance line at *"<15% extra drain per 8 h"* for NORMAL.
Measured from the battery snapshot taken at `clearRecords` over a **settled** 90 s
window — roles are promoted at the first election, and a window that starts at
warm-up bleeds pre-promotion drain into the per-role average (6.82 %/h instead of
7.5 for SUPER):

| world | duty cycle | NORMAL %/h | NORMAL %/8h | SUPER %/h | SUPER %/8h |
| --- | --- | ---: | ---: | ---: | ---: |
| `campus_quad`, stationary | off | 1.875 | **15.0** | 7.500 | 60.0 |
| `campus_quad`, stationary | on | 0.891 | **7.1** | 7.500 | 60.0 |
| `campus_quad`, mobile (default) | off | 2.423 | **19.4** | 6.422 | 51.4 |
| `campus_quad`, mobile (default) | on | 1.245 | **10.0** | 6.240 | 49.9 |
| `festival_crowd`, mobile | off | 2.811 | **22.5** | 7.574 | 60.6 |
| `festival_crowd`, mobile | on | 1.356 | **10.9** | 7.574 | 60.6 |

Three things fall out:

1. **The always-on model has zero headroom even for a still node.**
   `NORMAL_DRAIN_PER_HOUR` is `0.15/8` by construction, so a stationary,
   always-scanning NORMAL node spends *exactly* 15.0% per 8 h — the budget, not
   under it. Both engines reproduce this to 1e-3 (`closeTo(1.875)`).
2. **Mobility breaks it.** docs/03 §3's mobility term adds up to 2 %/h on top, so
   a moving population measures **19-25% per 8 h**. `skills/07`'s criterion is not
   met by an always-scanning NORMAL node, and no scan-interval tuning fixes that
   without also giving up discovery.
3. **The 3 s/7 s duty cycle brings it back inside.** 0.3 awake + 0.7 asleep at
   `sleepDrainFactor` 0.25 = **0.475** of the always-on drain → 8.7-12.4% per 8 h
   across both worlds. That is why the CLI gates the budget only in
   `--duty-cycle` mode: asserting it on the always-on arm would fail on a true
   statement about the model rather than on a defect. CI runs that arm on
   `campus_quad`.

SUPER never sleeps (`skills/07`: *"SUPER continuous"*), and it shows: **51-61% of
the battery in 8 h**. That is the strongest argument in the corpus for making the
opt-out user-visible rather than a buried setting — a phone at 30% should not be
handed a router role it cannot finish.

### 10.4 What sleeping costs: nothing measurable

Duty cycling throttles **scanning only**. An asleep node keeps beaconing and keeps
relaying what its route table already covers, which is the BLE asymmetry the spec
describes (the advertiser stays up; Android caps scan starts at 5 per 30 s).
Modelling a fully off radio would also need connection-interval negotiation, which
is out of scope. Full 150-message runs, both arms fed the same pre-generated
traffic plan (§7):

| world | seeds | delivery off → on | ≤5 hops off → on | relays vs flood-all off → on | NORMAL %/8h off → on |
| --- | --- | --- | --- | --- | --- |
| `campus_quad` | 42/7/1234/99/2026/555 | 98.8% → **99.6%** | 98.7% → 99.5% | 8.5% → 9.0% | 20.5% → **10.3%** |
| `festival_crowd` | 42/7/1234 | 93.1% → **93.6%** | 85.6% → 86.2% | 13.0% → 12.3% | 23.6% → **11.6%** |

Seed-mean delivery moves **+0.8** and **+0.5** points; per-seed swings run −1.3 to
+5.4 (crowd seed 1234: 91.3% → 96.7%). Read that as *delivery-neutral inside the
±5-point noise band at 150 messages*, not as "sleeping routes better" — six campus
seeds split 4 better / 1 equal / 1 worse. SUPER ratio stays in band (20-25%
campus, 18-22% crowd), flapping stays ≤0.22/node/min, overhead stays 8-14% of
naive flood, and the crowd's ≤5-hop tail is unchanged (§6: geometric, not
scan-limited). Every criterion that passed still passes in both modes.

Hence the flag, not a new default: turning the duty cycle on changes *when*
discovery happens, so per §7 it is a different experiment, and the golden vectors
stay where they are.

### 10.5 Telemetry now reported

`computeStats` / `_computeStats` in both engines: `batteryPercentPerHourNormal`,
`batteryPercentPerHourSuper` (measured, excluding charging nodes and any node
showing a net gain), `scansPerSec`, `relaysPerSec`, `scansSkippedAsleep`,

## 11. SOS: TTL sets the radius, repeating absorbs loss and movement

`docs/05` §3.2 specifies *"Broadcast SOS | All transports, flood (TTL=5) |
Maximize reach; no ACK needed"*, §3.3 Phase 3 specifies *"SOS mode | Repeated
flood of GPS + text over all transports (TTL=5)"*, and the Phase 3 exit criterion
is *"SOS reaches all within TTL"*. `docs/02` §"Broadcast SOS | All transports
flooding | Maximize reach" agrees.

Before this the engine had **one** broadcast with a TTL hardcoded to `7` — which
contradicted the documented 5 and was missing the repeat entirely. What ships now:

- the originator floods, then re-floods every `sosRepeatMs` (5 s) `sosRepeats`
  (3) more times — four floods;
- **each flood is a fresh message id.** The seen-cache is keyed on the id, so a
  repeat that reused one would be dropped by every node that already heard it.
  `sosId` is what ties the floods together;
- each flood carries `sosPos`, the sender's position *at that moment*, so a sender
  who is moving stays trackable. That is a reason to repeat beyond loss recovery;
- receivers collapse on `sosId`: four floods raise **one** alert holding the
  newest fix (`docs/04` §6 keeps the SOS channel opt-in precisely so an emergency
  cannot spam it). Copies arrive out of order, so the alert only ever moves
  forward in time — a late flood 1 must not overwrite the fix from flood 3;
- SOS bypasses MPR and the route table **at every hop** and floods to all peers.
  Suppression exists to delete duplicate copies; an emergency broadcast is made of
  them;
- SOS goes out on Wi-Fi Direct. The RF budget here is transport-independent, so
  what that buys is 40 ms per hop instead of 120. *"All transports"* is **not**
  modelled — one payload, one transport, one radio — and the code says so;
- a sender that goes offline or is switched off stops flooding.

### 11.1 Two knobs, because they fix different failures

Measured from the node furthest from the centroid (an SOS from the edge makes
reach a real test), 45 s window, `festival_crowd` 60 nodes, seeds 42/7/1234:

| arm | reach | last node heard | data tx |
| --- | --- | --- | --- |
| TTL 5, 1 flood (spec default) | 93.2% | 850 ms | 795 |
| TTL 5, 4 floods @ 5 s | 98.3% | **5 837 ms** | 3 177 |
| TTL 5, 6 floods @ 5 s | 98.3% | 5 837 ms | 4 900 |
| TTL 5, 4 floods @ 2.5 s | 97.2% | 2 536 ms | 3 098 |
| TTL 5, 11 floods @ 2 s | 100.0% | 6 208 ms | 8 657 |
| **TTL 7, 1 flood** | **100.0%** | 879 ms | **1 064** |
| TTL 7, 4 floods @ 5 s | 100.0% | 879 ms | 4 202 |

Three things fall out of that table. First, **repeats cannot fix a radius limit**:
six floods at TTL 5 buy nothing over four, because the missed nodes are beyond the
flood's reach, not unlucky — only 20 s of flooding plus mobility drift closes it,
at 8× the radio cost. Second, the 5 837 ms figure is the mechanism working: in a
TTL-limited flood the last node to hear it hears it **on a later flood**. Third,
`TTL 8` buys nothing over `TTL 7`, so 7 is the minimum that spans this world.

So `sosTtl` stays at the documented **5** as the default, and `festival_crowd`
overrides it to **7** with the reason in the scenario source: from an edge sender
that world is 6+ hops across (clusters 61–74 m apart against a 31.6 m LOS hop),
which is the same geometric floor §6 records for the crowd's ≤5-hop tail.

### 11.2 What repeating *is* for: loss and movement

At a TTL that already spans the world, repeats still earn their cost — 4 seeds,
`festival_crowd`, TTL 7: **89.4% → 100.0%** going from 1 flood to 4. And where
links are degraded they earn far more (`campus_quad`, TTL 7, 4 seeds):

| link conditions | 1 flood | 4 floods | 7 floods |
| --- | --- | --- | --- |
| as shipped (`linkRetries` 2) | 100.0% | 100.0% | 100.0% |
| no link-layer retries | 100.0% | 100.0% | 100.0% |
| shorter range (rx −80 dBm) **and** no retries | **40.8%** | **55.3%** | **64.5%** |

Each flood is an independent draw over marginal links, so repeating is
loss recovery — monotone in the repeat count exactly where loss is what bites, and
worth nothing where a single flood already covers everyone. Shortening the gap
without lengthening the total flood window makes it *worse* (97.2% at 4 floods
every 2.5 s vs 98.3% at 4 floods every 5 s): what matters is how long the sender
keeps trying, not how often.

### 11.3 "Reaches all" needs a denominator

Raw reach in a partitioned world is not a protocol failure. Measured over the
sender's **radio-connected component** (every node a chain of in-range links
reaches, at send time), SOS reach is **100% in all four scenarios and every arm**:

| world | component / online | component-relative reach | raw reach |
| --- | --- | --- | --- |
| `campus_quad` (20) | 19 / 19 | 100% | 100% |
| `festival_crowd` (60) | 59 / 59 | 100% | 93–100% depending on TTL |
| `sparse_village` (12) | 3 / 11 | 100% | 27.3% |
| `partitioned_pair` (10) | 4 / 9 | 100% | 44.4% |

`sparse_village` and `partitioned_pair` are built to be disconnected, so 8 of 11
and 5 of 9 online nodes simply have no chain to the sender. The exit criterion is
therefore reported both ways, and `dart run bin/mesh_sim.dart --sos` prints both
plus the missed ids — in a *separate* simulation, because an SOS fan-out costs
thousands of transmissions and folding it into the main run would make the
overhead ratio meaningless.

Cost, stated plainly: four floods in `campus_quad` are **178 → 691** data
transmissions (3.9×), tracked as `stats.sosFloods`. That is why the repeat count
is a knob with a `0` setting rather than a constant.

## 12. A node must never process a copy of its own message

Found by a render smoke test for the SOS card, which reported
**"20 of 19 online nodes heard"**. The impossible denominator was the originator
holding its own alert.

A node never hears its own transmission, but it does hear **peers relaying it
back**, and `onMsgReceive` had no rule for that copy. So the originator:

1. accepted its own broadcast as a fresh delivery (raising its own SOS as a
   received notification, and putting a message it wrote into its own inbox);
2. marked it seen and **re-flooded it** — `decideForward` on a broadcast returns
   every peer — so each returning copy triggered a fresh fan-out from the source.

On a broadcast SOS, which already floods to every peer at every hop, that is a
storm amplifier bounded only by TTL. Both engines now treat a copy of the
receiver's own message as the duplicate it is: counted, logged as *"own message
returned by X — not re-flooded"*, and **still recorded as coverage evidence**
(`heardRelays`), because a neighbour relaying my message back is genuinely a
neighbour that holds it. `sendMessage` echoes a note-to-self straight into the
inbox instead of putting it on the radio, since with the guard in place such a
message could otherwise never be delivered at all.

### 12.1 Measured, six seeds, identical traffic plan per arm

| world | relay tx | delivery | acks | retries |
| --- | --- | --- | --- | --- |
| `campus_quad`, warm | 3 009 → **2 458** (−18.3%) | 99.3 → **99.7%** | 97.5 → 98.2 | 12.7 → 15.7 |
| `festival_crowd`, warm | 30 734 → **29 491** (−4.0%) | 84.7 → **86.2%** | 63.7 → 65.5 | 84.8 → 80.5 |

SOS: 80 → 76 radio receipts in `campus_quad` (the four phantom self-receipts
gone), sender no longer holds its own alert, component reach still 100%.

**Latency moved the other way** in these samples — campus p95 1 729 → 2 467 ms,
crowd 7 355 → 8 152 ms — with per-seed swings of 1.1–4.6 s, so it is reported and
not claimed either direction. The guard is a correctness fix that happens to be
cheaper; it was not adopted *for* the transmission saving.

### 12.2 Why the golden vectors moved, and why that is legitimate

The guard changes **how many transmissions happen**, and every transmission draws
from the RNG for its loss roll — so the stream diverges and the whole run
rearranges. This is not the "a new field must consume no RNG" rule of §9 being
broken; it is a behaviour change, and it is the reason the fixture is regenerated
rather than patched:

| field | before | after |
| --- | --- | --- |
| `relayTx` | 253 | 289 |
| `ogmTx` | 16 874 | 16 655 |
| `retriesSent` | 1 | 0 |
| `acksReceived` | 19 | **20** |
| `sumHopCounts` | 36 | 33 |
| `avgHops` | 1.80 | 1.65 |
| `avgLatencyMs` | 474.4 | 526.6 |
| `p95LatencyMs` | 950.4 | 1 356.1 |

Regeneration is deterministic (running `npm run golden` twice is byte-identical),
`deliveredUnicast` stays 20/20, and both engines carry the same guard — CI's
Dart job compares against the same fixture, so agreement is checked, not assumed.

### 12.3 Two tests corrected, not loosened

- *"delivers a multi-hop unicast along a routed path"* was picking **the sender
  itself** as its out-of-range target, because `canReach(a, a)` is `false` by
  construction (`rf.ts`). It only ever passed because the engine bounced the
  node's own message back to it through the mesh — the defect was load-bearing for
  the test. The pick is now explicit.
- The per-seed `mpr / route-flood ≤ 0.85` pin measured **0.947** on seed 42 after
  the guard. Cause, from the cold-start A/B: `route-flood` is the arm that floods
  most, so it was the arm most inflated by the amplifier — on that seed its
  transmissions fell 37% (6 902 → 4 315) while MPR's fell 4% (4 239 → 4 087).
  Part of the previously measured advantage was *the amplifier being proportional
  to how much you flood*. Six-seed means: `mpr/route-flood` 0.752 → **0.736**,
  `mpr/flood-all` 0.085 → 0.093. The cut is now pinned on the **mean** (≤ 0.80)
  plus a hard per-seed "never worse than routing without suppression", with this
  reasoning in the test body.

## 13. Hop traces and the capture log (roadmap Phase 4)

*"Hop visualization: 'via 2 nodes • SUPER Amir' hop trace for transparency."*
Rendering that string honestly needs more than a node list, so two things were
added.

**`HopRecord`** — one per node that accepted a *fresh* copy: arrival time, who
handed it over, the link budget in dBm from the `docs/05` §1.1 model, the hop
index, the action (`delivered` / `relayed` / `suppressed` / `queued` / `expired`)
and `decideForward`'s own reason string. A `wait-mpr` record is **provisional**:
when the 300 ms wait ends in suppression, `onMprDecide` rewrites it, so the trace
reports the outcome rather than the intention. Traces are always on — they are
bounded by the path length.

**`MeshLogEntry`** — a pcap-like capture of radio and protocol events
(`tx`, `loss`, `duplicate`, `deliver`, `decision`, `queue`, `election`, `ack`,
`sos`, and `ogm` behind its own flag). Bounded at `maxLogEntries` 2 000 and **off
by default**, because a 60-node crowd emits hundreds of thousands of beacons.

### 13.1 `path` is a tree; the roadmap sentence wants a chain

`path` (and therefore `hopTrace`) lists every node that accepted a fresh copy, so
it branches the moment a relay fans out. A 4-hop delivery in the 20-node world
lists **15** nodes. `deliveredChain(hopTrace, to)` walks `via` backwards from the
recipient to recover the actual route, and on every sampled delivery
`chain.length === hops` while `path.length` runs to 12–15. The originator is not
in the result (it never receives its own message), so a renderer prepends
`delivery.from`. Retransmissions share the message id and so the same trace, where
first-record-per-node wins.

Probe of the deepest trace in a 40-message campus run (`m11`, 4 hops, ~924 ms
end-to-end):

```
node-15  hop 0  "MPR fallback: no relay heard"          → 8 neighbours
node-11  hop 1  relayed   "route via node-0"
node-0   hop 2  relayed   "destination in range"
node-8   hop 2  SUPPRESSED "MPR: heard relays cover all my neighbours"
node-13  hop 2  SUPPRESSED "MPR: heard relays cover all my neighbours"
node-5   hop 3  delivered
chain: node-15 → node-11 → node-0 → node-5   (length 3 == hops)
```

The two suppressed rows are the whole point of the panel: `path` alone cannot show
that MPR kept two nodes quiet, and "via 2 nodes • SUPER Amir-11" is computed from
the chain, not from the tree.

### 13.2 Capture is provably inert

One 40-message campus run: hop actions `{delivered 80, relayed 221, suppressed
60}`; log kinds `{tx 820, decision 436, duplicate 378, deliver 83, ack 40, loss
24, election 8}` = 1 789 entries under the 2 000 cap; `deliveryRatio` 1.000
unchanged. With `captureLog` **and** `captureOgm` on, `totalForwarded`,
`controlOverhead`, `totalDelivered`, `avgLatencyMs` and every node position are
**identical** to the uncaptured run, and the golden vectors are byte-identical —
logging consumes no RNG, which is the property that makes it safe to leave on.

`clearRecords()` drops the log with the rest, so a re-baselined measurement never
carries events from before the baseline. The DTN last resort (retries exhausted →
OppQueue, `docs/03` §8) is logged as a `queue` event; it was not, and writing the
test for it is what exposed that.

CLI: `--trace` prints each delivered message's route as the roadmap phrases it
(`via 2 node(s) • SUPER node-11`) followed by the hop table — dBm, arrival,
action, reason; `--capture` prints the log tail; both are in `--json` as `traces`
and `logTail`. In the UI, the chat log's **trace** button draws the route on the
canvas as a numbered polyline and opens the hop panel, and the mesh log panel
filters to the traced message.

## 14. Group channels: the crossover is proximity, not group size

`docs/04` §4: *"Group chat: MLS-style or simple sender-key distribution over 1:1
channels: each group has `groupKey` rotated on member leave"*. roadmap Phase 1:
*"Broadcast pager channel (public) + private 1:1 + group (3-10 members)"*. Phase 4
adds *"Group UX: invite via QR, admin rotate key, leave/rejoin sync"*.

What the engines implement: a group of 3-10 members with an admin, a key epoch
that rotates on **every** membership change and on manual admin rotation, and two
delivery modes —

- **`scoped-flood`** (default): one message addressed to `GROUP`, relayed by the
  whole network on the *normal* policy (MPR included, unlike SOS), accepted only by
  members holding the current epoch. The network never learns the membership, which
  is the point: a non-member that relays a group message learns nothing from it.
- **`per-member-unicast`**: one routed message per member, which the route table can
  aim, and which gets an ACK and retries each.

### 14.1 Measured: 20 sends per arm, seeds 42/7/1234

Transmissions **per group message**, and group delivery ratio:

| world | members | layout | scoped flood | per-member unicast | cheaper |
| --- | --- | --- | --- | --- | --- |
| campus (20) | 3 | clustered | 75.7 tx · 100% | **4.0 tx** · 100% | unicast 19× |
| campus | 3 | spread | **66.8 tx** · 100% | 37.8 tx · 100% | unicast 1.8× |
| campus | 5 | clustered | 75.7 tx · 99.6% | **8.3 tx** · 100% | unicast 9× |
| campus | 5 | spread | **75.7 tx** · 100% | 158.8 tx · 99.6% | flood 2.1× |
| campus | 10 | clustered | **75.7 tx** · 99.8% | 116.7 tx · 99.8% | flood 1.5× |
| campus | 10 | spread | **75.7 tx** · 99.8% | 298.6 tx · 99.1% | flood 4.0× |
| crowd (60) | 3 | clustered | 519.6 tx · 100% | **4.0 tx** · 100% | unicast 130× |
| crowd | 5 | clustered | 519.6 tx · 100% | **8.3 tx** · 100% | unicast 63× |
| crowd | 10 | clustered | 519.6 tx · 99.8% | **18.8 tx** · 99.8% | unicast 28× |
| crowd | 3 | spread | **519.6 tx** · 92.5% | 608.1 tx · 90.0% | flood 1.2× |
| crowd | 5 | spread | **519.6 tx** · 96.3% | 273.9 tx · 98.3% | unicast 1.9× |
| crowd | 10 | spread | **519.6 tx** · 95.0% | 3020.6 tx · 91.9% | flood 5.8× |

Three things the table says:

1. **A scoped flood costs the same whatever the group.** 75.7 tx in the campus and
   519.6 tx in the crowd for 3 members or 10 — the whole network relays it either
   way, and only the accept count changes. That is the price of not revealing
   membership, and it is a fixed price.
2. **Per-member unicast cost tracks how far the members are, not how many.** All
   three clustered crowd rows are 4-19 tx (every member is a direct peer: one
   transmission each) while the spread rows are 274-3021 tx (each copy fans out
   when the route is unknown or long). Size matters only through distance.
3. **Delivery is a wash except at the edges.** Both modes reach ~100% in the campus.
   In the crowd the flood is better for spread groups (95.0% vs 91.9% at 10 members)
   because it has no per-member ACK/retry tail and its TTL-5 fan-out covers more of
   a sparse geometry than ten individually routed paths; unicast is better for the
   5-member spread row (98.3% vs 96.3%) because a retry recovers what one flood lost.

So `scoped-flood` ships as the default: its cost is predictable, it needs nothing
from the route table, and it is the only mode whose privacy property holds (a
per-member unicast reveals the membership to every node on each path).

### 14.2 Why there is no `auto` mode: the sender cannot price a unicast

The obvious follow-up is to let the sender choose per message. It cannot, and the
reason is worth recording because it looks like it should work.

The sender *does* hold an OGM entry per member with a hop count. But that hop count
is **not a distance oracle**: for members it reaches in one hop, the table said 3-4.
That is correct BATMAN behaviour — the best entry is the one with the highest link
quality, and in a dense world the direct link can have worse tq than a gossiped
path, so the recorded `hopCount` describes the *chosen* route, not the *shortest*
one. `decideForward` then sends to a direct peer anyway, because "destination in
range" is checked before the route table.

Predicting unicast cost from those numbers does not work either. Realised
transmissions per summed OGM hop, across the twelve rows above: **0.6, 1.0, 1.2,
5.3, 9.4, 13.0, 17.1, 22.7, 76.0, 107.9** — a 180× spread with no usable signal.
The dominant term is how often a member copy falls back to a fan-out because the
route was unknown *at that instant*, which is a property of scan timing rather than
of geometry.

So: two modes, a measured default, and `--group [N]` in the CLI, which reports both
modes on the world you are actually running and prints which is cheaper and why.
An `auto` mode is a legitimate follow-up, but it needs a fresher distance estimate
than the OGM table gives — a direct-peer check plus a measured fan-out rate, not a
hop count.

### 14.3 Key rotation is network-wide, and that is the semantics

Rotation discards the old key everywhere, so a message already in flight under
epoch *n* becomes unreadable to **every** member once the group rotates to *n+1* —
not only to the node that left. Both engines count those copies as
`groupEpochRejected` and never deliver them, and a test pins that a message sent
under epoch 0 produces zero deliveries after a rotation to epoch 1.

The departed node keeps **relaying**: the bytes are not secret to the network, only
unreadable to it. That is the property the leave test asserts (its `txCount` rises
while its inbox stays empty), and it is why a scoped flood does not need membership
knowledge to work.

### 14.4 Accounting

Group traffic is excluded from `unicastDeliveries` — a 10-member group would
otherwise flatter `deliveryRatio` tenfold — and from `sentBroadcast`, which would
deflate `broadcastReach`. It gets `sentGroup`, `groupReceipts`, `groupExpected` and
`groupDeliveryRatio` instead, where `groupExpected` counts *member deliveries that
should have happened* so the ratio means the same thing in both modes (one message
in flood mode, N in unicast mode).

`groupReceipts` is incremented in `recordDelivery`, not at a delivery call site,
because group traffic arrives by two different roads and a counter in only one of
them silently reports 0% for the other — which is exactly what the first
measurement run of §14.1 showed for every unicast row before the counter moved.

Not implemented, and named so nobody assumes otherwise: sender-key distribution
over 1:1 channels (docs/04's actual key-agreement scheme), QR invites, rejoin
history sync, and CRDT anti-entropy for group history (roadmap Phase 1 item 32).
The simulator models *who may read what, and what it costs to get it there*; the
key agreement underneath is the research item.

Delivery never drops — but look at the relay column. 150 nodes costs **46**
transmissions for 20 messages and 200 nodes costs **15 933**. That is not a trend, it
is a cliff, and it is worth more than the headline "10-200 works".

### 15.1 Diagnosis: a beacon cannot describe a 179-peer neighbourhood

Counting transmissions per message id and reading the hop traces put the whole cost
in four messages:

| message | transmissions | hops | nodes that accepted a copy | relays | reasons on the path |
| --- | --- | --- | --- | --- | --- |
| `m6` | 7 038 | 3 | 187 | 185 | route via node-7 / node-10 / node-0 |
| `m23` | 3 681 | 3 | 183 | 181 | MPR fallback: SUPER heard but my neighbours are not covered |
| `m5` | 218 | 4 | 110 | 105 | MPR fallback: no relay heard |
| `m24` | 90 | 3 | 39 | 34 | MPR: heard relays cover all my neighbours |

The mechanism: `MPR_NEIGHBOR_ADVERTISE_LIMIT` is 30, so at 200 nodes a beacon
advertises 30 of a node's ~179 neighbours. `relaysCoverPeers` compares the union of
the heard relays' *advertised* lists against this node's own peer list — 30 entries
against 179 — and can only answer "no". Every relay therefore takes the fallback, and
the fallback flooded to **all** peers. One message, 185 relays, ~180 peers each:
7 038 transmissions to move a message three hops.

At 150 nodes the same truncation exists but the routes happened to resolve, so the
fallback never fired and the run cost 46. The cliff is not density itself; it is
density *plus* a coverage test that cannot be answered.

### 15.2 Fix: bound the fallback, and bound it by direction

The fallback now caps its fan-out at `DENSE_FALLBACK_FANOUT` = 6 peers, **only** when
the node has more peers than one beacon can advertise. Below that limit the peer list
is complete, the coverage answer is exact, and the branch is not taken: `campus_quad`
peaks at 12 peers and `festival_crowd` at 24, so every measurement elsewhere in this
document stands and the golden vectors are byte-identical.

The six are chosen **one per angular sector**, best link per sector, then
strongest-first to fill any empty sector. Direction is the point: the strongest links
are the nearest peers, and the nearest peers are all on one side of a node, so
choosing by RSSI fans out into a wedge and leaves the rest of the world to chance.
The tie-break is on the peer id as well as the link, because JavaScript and Dart sort
equal keys differently and the two engines must pick the same six peers.

Measured at 200 nodes, 30 messages, seeds 42 and 7:

| fallback | delivery | tx per message | p95 |
| --- | --- | --- | --- |
| unbounded (all peers) | 100% | 531.1 | 1 367 ms |
| capped at 6, strongest RSSI | 96.7% | 204.8 | 1 415 ms |
| **capped at 6, one per sector** | **98.3%** | **125.5** | **1 294 ms** |

Across the range, before → after (transmissions per message):

| nodes | before | after | change | delivery |
| --- | --- | --- | --- | --- |
| 20 | 21.9 | 21.9 | inert | 100% → 100% |
| 50 | 170.4 | 56.7 | **−67%** | 100% → 100% |
| 100 | 1 014.0 | 141.4 | **−86%** | 100% → 100% |
| 150 | 2.3 | 2.3 | inert | 100% → 100% |
| 200 | 531.1 | 125.5 | **−76%** | 100% → **98.3%** |

200 nodes is the only place the cap costs anything, and it costs one message in 60
(both seeds 97%). It buys a 4.2× cut in transmissions and stays inside the documented
≥90% bar; a test in each engine pins both numbers so neither can drift silently.

### 15.3 The alternative that was tried and rejected

Assume coverage instead of bounding the fan-out: if a heard relay's advertised list is
truncated *and* its own peer count is at least ours, treat our neighbours as covered
and stay quiet. It is cheaper still — 11 474 transmissions at 200 nodes — but it
delivers **95.0%**, and it is worse than bounding at 50 and 100 nodes too (1 710 and
5 996 tx against 922 and 4 849).

The reason is worth keeping: *assuming* coverage loses messages, because the
assumption is wrong for the ~10% of the world that any one relay cannot hear.
*Bounding* the fan-out does not lose them, because a K-ary fan-out still covers a
homogeneous dense world in log_K(N) hops — every relay's peers are everyone's peers.

### 15.4 What the density numbers do **not** claim

Two limitations, stated because the table above is easy to over-read.

**There is no collision model.** At 200 nodes in 10 000 m² every node hears ~179
others; on real BLE that channel is interference-limited and marginal link quality
would be far worse than a distance-plus-walls model says. These figures bound the
*protocol's* behaviour in a dense geometry, not a deployment's.

**`ogmTx` counts receptions, not transmissions.** Each OGM is accounted once per
receiving peer, so control traffic reads as O(N²): 3 355 408 at 200 nodes against
4 482 at 10. On a real radio a discovery beacon is *one* advertising packet heard by
everyone in range, so transmission cost is O(N) and only reception cost is O(N²).
Splitting that counter in two is a legitimate follow-up; it would move the golden
fixture's `ogmTx` field, so it was not folded into this change.

**Wall clock.** A 200-node run of 38 simulated seconds takes 24.6 s, about 0.65× real
time. That is why the scale case lives in the two test suites (six messages each)
rather than in the CI acceptance matrix, which runs at 20 nodes.

Battery at density is unremarkable and consistent with §10: NORMAL burns 2.40-2.51%
per hour always-scanning (19-20% per 8 h, above the `skills/07` budget), and the duty
cycle is what brings it inside.

## 16. The crowd's ≤5-hop tail: decomposition, and two levers that do not work

§6 left this open: in `festival_crowd` (60 nodes, 80% mobile, clusters 61-74 m apart
against a 31.6 m line-of-sight hop) delivery is 91-95% but only ~84% of sent messages
arrive within five hops, against the 90% bar `skills/08` sets for the 20-node case.
Two questions: what is the tail actually made of, and can it be bought?

### 16.1 What the tail is made of

For every message, the shortest path in the *real* in-range graph at send time (BFS,
ignoring loss) was compared with the hops the delivered copy actually took. 450
messages, seeds 42/7/1234:

| outcome | count | share | addressable? |
| --- | --- | --- | --- |
| delivered within 5 hops | 380 | 84.4% | — |
| BFS distance ≥ 6 at send time | 10 | 2.2% | no — geometry |
| no path at all at send time | 8 | 1.8% | no — DTN territory |
| lost or TTL-expired | 26 | 5.8% | in principle |
| delivered, but with more hops than BFS | 26 | 5.8% | in principle |

The hop-by-hop pairs say where the extra hops come from: `bfs3→hops4` 25 times,
`bfs5→hops6` 15, `bfs2→hops3` 13, `bfs4→hops6` 9 — and, in the other direction,
`bfs5→hops4` 3 times and `bfs3→hops2` once. A message that arrives in *fewer* hops
than the send-time shortest path proves the graph moved while it was in flight, so a
share of the "+1 hop" cases is churn rather than a routing error.

Routing is not choosing badly: `receiveOGM` already prefers fewest hops and breaks
ties on link quality, and `decideForward` checks "destination in range" before
consulting the table at all. There is no shorter path to find.

So the honest arithmetic: 24 of the 70 messages that miss the bar (34%) miss it
because routing took one or two hops more than the send-time optimum, and 4 of 450
(0.9%) could not have made it in five hops at any cost. Fixing *all* of the routing
churn would put w5 at 89.7% — still short, and not achievable anyway, because the
churn is the world moving.

### 16.2 Two levers, measured, and neither works

`festival_crowd`, 150 messages, **six** seeds (42/7/1234/99/2026/555):

| arm | w5 | delivery | avg hops | p95 | OGM tx | relay tx | retries exhausted |
| --- | --- | --- | --- | --- | --- | --- | --- |
| as shipped (OGM 2 s, 2 retries) | **84.1%** | 91.7% | 2.83 | 6 700 ms | 817 k | 39 294 | 41.0 |
| OGM 2 s → 1 s | 83.0% | 89.7% | 2.77 | 5 816 ms | 1 598 k | 40 781 | 40.7 |
| OGM 2 s → 0.5 s | 82.2% | 88.8% | 2.75 | 6 400 ms | 3 176 k | 42 258 | 40.8 |
| retries 2 → 4 | 84.3% | **93.2%** | 2.90 | 10 860 ms | 809 k | 51 872 | **33.2** |
| retries 4 + ACK timeout 2.5 s | 81.0% | 88.1% | 2.77 | 6 591 ms | 796 k | 54 249 | 41.5 |
| OGM 1 s + retries 4 | 84.7% | 91.9% | 2.84 | 10 566 ms | 1 589 k | 57 876 | 35.5 |

**Faster beacons do not produce fresher routes.** Doubling the OGM rate costs 1.95×
the control traffic and *loses* 1.1 points of w5 and 2.0 points of delivery;
quadrupling it costs 3.9× and loses more. The mechanism is visible per seed: with
1 s beacons, seed 99 collapses from 81% w5 to 62%. A denser beacon stream in a
60-node mobile world adds contention and more gossiped duplicates through the tq
windows, and the route it converges on is no better — because the route was never the
problem (§16.1: the graph moves faster than any beacon interval can track).

**More retries buy delivery, not hop count.** Going from 2 to 4 retries lifts
delivery 91.7% → 93.2% and cuts give-ups 41.0 → 33.2, which is real, but w5 moves
+0.2 points (inside the noise) and p95 rises 6 700 → 10 860 ms, because a retry costs
a whole ACK timeout. That is the trade §7 already warns about, and why docs/04's
per-hop latency budget is measured on first-attempt traffic only.

**Both together** reach w5 84.7% and delivery 91.9% for 1.95× control traffic, +47%
relay traffic and +58% p95. There is no combination here that reaches 90% w5.

### 16.3 What this changes

Nothing in the defaults, and that is the result: `ogmIntervalMs` stays 2000,
`maxRetries` stays 2, and `festival_crowd` keeps its shipped parameters. The
scenario override that §11 did add (`sosTtl` 7) is a different kind of thing — it
corrects a *radius* the flood physically cannot cross, which no amount of tuning
fixes. This tail is not that.

The claim this document can defend is narrower and better supported than "tune the
crowd to 90%":

- at 20 nodes, the acceptance case, w5 is **99.7%** across six seeds (§2);
- at 60 nodes with 80% mobility and a 3-hop geometric floor between clusters, w5 is
  **84.1%**, and the tail decomposes into 2.2% geometry, 1.8% no-path, 5.8% loss and
  5.8% in-flight churn;
- the two obvious levers are measured and do not close it, one of them actively
  harms.

What *would* close it is not a protocol knob: more radio range or a denser deployment
(the 3-hop floor between clusters is geometry), a bar expressed as ≤6 hops for worlds
whose diameter is 6, or measuring w5 over messages that had a path at send time
(which puts it at 85.9%, still short). Recording that is more useful than shipping a
tuning change that three seeds would have justified and six refute.

### 16.4 The methodological point, with numbers

On three seeds, "OGM 1 s" measured **+2.6 points** of w5 and +1.3 of delivery and
looked like a clear win worth shipping as a scenario override. On six seeds the same
arm measures **−1.1** and **−2.0**. The sign flipped, not just the magnitude, because
one hard seed (99) went 81% → 62% and three easy seeds improved.

§7's rule — compare on the mean across seeds, and treat a few points as noise — is
not a formality. For a 60-node mobile world the band is wide enough to invert a
conclusion, so any parameter change proposed on this evidence needs six seeds before
it is believed, and the per-seed spread printed next to the mean.

## 17. Group history: hash-beacon anti-entropy, and the graph it can repair over

**Roadmap Phase 1 asks for "SQLite + CRDT for group/broadcast history (hash beacon
anti-entropy)". §14 established half of why it matters — a rotation makes older copies
unreadable — but the other half was simply missing: a member that was asleep, out of
range or switched off while a scoped flood went by missed that copy for good. Nothing in
the engine repaired it, and `groupDeliveryRatio` recorded the loss without offering any
way back.**

Both engines now implement the repair, and `npm run history` /
`dart run bin/mesh_sim.dart --history` measure it. SQLite is storage and stays app-side;
what is simulatable is the protocol, and the protocol is where the interesting boundary
turned out to be.

### 17.1 The mechanism

Each member keeps the group messages it holds as a **grow-only set keyed by message id**
— a G-Set CRDT — so merging two members' histories is a union: idempotent, commutative
and associative. That property is what lets the rest of the design be lazy: beacons can
be lost, duplicated or reordered, and a reply can arrive twice, without the protocol
caring.

* **Beacon.** Every `historyBeaconMs` (10 s) a member offers each co-member it can
  *hear* a digest of what it holds: `HISTORY_BUCKETS = 16` XOR-folded FNV-1a bucket
  hashes plus an entry count. Measured size: **156 characters whether the group has said
  nothing or 400 messages**, which is `wireSizeOf(156) = 256 B` — one BLE packet, and
  the only part that grows with history is the decimal count (158 characters at 400
  entries).
* **Request.** A peer whose buckets differ asks for *those buckets* and lists the ids it
  already holds in them (capped at 64).
* **Reply.** The responder sends the entries in those buckets that the requester did not
  list, capped at `historyReplyMax = 32`, sorted by id.
* **Merge.** Union by message id. Entries under an older key epoch are refused and
  counted (`historyEpochDropped`), because a rotation made them unreadable (§14).
* **No acknowledgements.** The next beacon is the retry. Acknowledging every digest would
  cost more radio time than the repair it reports on.

FNV-1a is not a cryptographic hash and does not need to be: a digest here only has to
tell two sets apart, and the ids it covers are already visible to every relay on the
path. Both engines assert the same fixed points — `fnv1a32("m1") = 2486071275`,
`historyBucket("m1") = 11` — so a drift in either implementation fails CI.

XOR folds a *set*: feeding it the same id twice cancels that id out. That is not a defect
to fix but the reason the store is keyed by id and the merge is a union, and both test
suites assert the cancellation explicitly rather than pretending it cannot happen.

### 17.2 The defect a test caught: a bounded reply has to know what to skip

The first version replied with the first 32 entries of the differing buckets. With a
20-message absence and `historyReplyMax = 8`, the returning member converged to 8
entries and **stopped**: every round re-offered the same head of the same sorted list,
because the responder had no idea what the requester had just accepted.

The fix is the id list in the request. Once the responder can exclude what the requester
already holds, each capped round advances, and a 20-message absence converges in
`ceil(20/8)` rounds plus whatever link loss adds. This is why the request is bigger than
a bucket list, and why the cap is safe.

### 17.3 Measured: repair works, and it is transitive

Five members, 20 messages, one member out of radio range for the whole conversation
(`campus_quad`, seed 42, settled 90 s), then the member returns:

| membership | member peer graph | recovered | converged | rounds | packets | payload |
|---|---|---|---|---|---|---|
| spread across the world | 6 of 20 directed links, **not connected** | 20/20 | **no** (>300 s) | 2 | 171 | 29.8 KB |
| 5 nearest nodes | 20 of 20 links, connected | 20/20 | **yes, 8.8 s** | 4 | 60 | 15.7 KB |
| either, with `historyBeaconMs: 0` | — | **0/20** | no | 0 | 0 | 0 |

Repair is **transitive**, which the capture log shows directly: in a three-member line a
copy the middle member lost reaches it from the sender — `field team: Amir-0 and
Bianca-1 disagree on bucket 1 (20 vs 19 entries) — requesting` — and then reaches the
returning member from the middle. A run repairing 20 messages cost 32 beacons, 8
requests, 4 replies, 44 packets and recovered 21 entries (the extra one is the middle
member's own loss).

Idle cost, when there is nothing to repair: **31 beacons/minute for a five-member group,
81 B/s of background traffic**. For scale, the same 20-node campus sends ~2,800 relay
transmissions in 300 s of ordinary message traffic (§6), so the digest beacons are noise
next to the routing plane they ride on.

### 17.4 The boundary: anti-entropy converges over the peer graph, not the membership

The spread arm recovered every message the returning member had missed and still never
converged. That is not a bug and not a timeout that a longer budget would fix; it is the
shape of the protocol.

Beacons go to co-members **in range** and nowhere else. So the graph being reconciled is
"which members can hear which", and in the spread arm only 6 of 20 directed member pairs
can carry a beacon and the graph is disconnected: two members who are never in range of
each other, with no chain of co-members between them, can never compare digests. Whatever
one of them holds alone stays alone.

The honest statement of the division of labour:

* the **scoped flood** (§14) is responsible for getting a message to every member, across
  hops, through relays that cannot read it;
* **anti-entropy** is responsible for the last hop of a loss — the member that was asleep,
  out of range, or switched off — and for repairing it cheaply, without re-flooding;
* a membership spread beyond radio range needs the flood to have worked in the first
  place. Repair cannot substitute for reach, and the measurement above is exactly where
  the two responsibilities meet.

The alternative — letting digests relay across the mesh — would converge a spread
membership and would cost what a scoped flood costs on every interval, forever, to
repair traffic that mostly arrived. It was not implemented, and the numbers above are the
reason.

### 17.5 What a key rotation costs that §14 did not show

§14 measured a rotation's effect on delivery. It has a second effect: because entries
under an older epoch are unreadable to everybody, the engine does not offer them, so
**the repairable history of a group is only ever as old as its last membership change**.
In a group that rotates on every join and leave (the shipped policy, and the one
`docs/04` §4 asks for), anti-entropy can repair a member's absence but can never rebuild
the group's past. Both suites assert this: after a rotation the pre-rotation message is
not offered, not recovered, and `historyEpochDropped` stays at 0 because nothing stale
was ever put on air.

That is a design consequence worth stating to whoever builds the app: if history is a
product feature, the key schedule has to change with it (per-message keys, or a rotation
that re-wraps history), and no amount of anti-entropy will substitute.

### 17.6 Accounting

Sync packets are counted apart (`sentSync`, `historyBeacons`, `historyRequests`,
`historyReplies`, `historyEntriesSynced`, `historyEpochDropped`, `historyBytes`),
excluded from `deliveryRatio` and from the chat log, and reported on the dashboard. A
node with no groups arms no beacon chain, so a run that never creates a group consumes no
extra randomness: **the golden vectors are byte-identical** in both languages.

## 18. The atrium does become a router — if it is charged

**Roadmap Phase 2's field-test criterion names a building feature: "atrium should become
SUPER". It is the rare hardware criterion the simulator can answer in advance, so it was
answered, and the answer has a condition on it that the criterion does not mention.**

The most open node in a world — the one that hears the most peers at the strongest average
RSSI, found by measurement rather than assumed from the floor plan — was made healthy
(battery 1.0, ten hours of uptime, `pdr` 0.99, stationary) and the election was run for two
cycles. It became SUPER in **all four worlds**: `campus_quad`, `sparse_village`,
`festival_crowd` and `partitioned_pair`, with a score at or above the mean of the elected
set in each.

Left as spawned, the same node stayed NORMAL in **three of the four**. That is not noise;
it is the coverage score doing what `docs/03` §3 specifies.

### 18.1 The decomposition

```
score = 0.30 · log(1+peers)/log(51)   position
      + 0.25 · (avgRssi + 100)/70     position
      + 0.20 · battery                health
      + 0.15 · min(uptime/60, 1)·(1−mobility)
      + 0.10 · pdr                    health
      + 0.10 if charging
```

Position carries 0.55 of the weight and health 0.45 — but position is *compressed* and
health is not. The peer term is normalised logarithmically against 50 peers, so it
saturates: going from 19 peers to 199 buys 0.175 of the term, i.e. 0.053 of score, while
going from a drained phone to a healthy one moves up to 0.35.

A drained atrium phone (battery 0.30, 20 minutes of uptime, `pdr` 0.90) against a healthy
corridor phone with nine peers, both with peers 12 m away in every direction:

| candidate | peers | peer term | total score |
|---|---|---|---|
| drained | 19 | 0.229 | 0.5122 |
| drained | 60 | 0.314 | 0.5973 |
| drained | **199** — more peers than any world in §15 has nodes | 0.404 | **0.6879** |
| healthy | 9 | 0.176 | **0.7083** |

**No peer count available in a ≤200-node world lets a drained phone outrank a healthy one
with nine peers.** The drained phone at 199 peers does clear the 0.60 promotion threshold;
it simply is not in the top 20%, because healthier nodes are above it.

### 18.2 Is the weighting right?

Arguably yes, and for the reason this product exists: a mesh that has supposed to survive a
day without chargers should not elect a router that is about to die. `docs/03` §3's weights
say so explicitly, and §5's hysteresis (demote below 0.50 for two cycles) is the same
instinct applied over time. The charging bonus of +0.10 points the same way, and
`skills/02`'s "NORMAL never auto-promoted if battery saver is on" is the hard edge of it.

The limitation is worth naming anyway, because a field test could hit it: the logarithmic
normalisation means the score **cannot express "dramatically better placed"**. A node
hearing 199 peers and one hearing 60 differ by 0.09 of score. In a deployment whose whole
topology rests on one unusually open position — a courtyard, an atrium, a ridge — the
weights under-reward exactly the node the roadmap expects to win. The obvious alternative
is to normalise peer count against the *observed* maximum in the world rather than a fixed
50, which would make openness decisive in sparse worlds and still bounded in crowds. It is
**not shipped**: §15 is the record of what happens when a coverage rule assumes "everyone
hears everyone" and meets a 200-node world, and this is the same trap approached from the
other side. If the field test shows the atrium losing to a corridor, that is the lever to
pull, and it needs six seeds before anybody believes it (§16.4).

### 18.3 What the field test has to record

`docs/09` §5 now predicts the atrium result *conditionally*, and the capture schema's
`sample` records carry `role`, `battery`, `charging` and `awake` for exactly this reason.
On the day the criterion to check is not "the phone in the atrium is SUPER" but:

1. the elected set is the top 20% by score, and
2. the atrium phone is in it **if** it is healthy — with battery, uptime and packet loss
   recorded next to its placement, because without those three columns a win is a
   coincidence and a loss is uninterpretable.

Both engines assert the healthy-node result in all four worlds and the score arithmetic
above (`the atrium becomes a router`, in `src/__tests__/simulation.test.ts` and its Dart
twin).

## 19. The community relay programme: a quota, not a device

**Roadmap Phase 5 proposes: "Community relay program: *Keep Duman on a plugged tablet at
your café/campus → community SUPER*". It is one line, it sounds free, and it is simulatable
today — a plugged tablet is a node with `charging: true`, `stationary: true`, a full battery
and no opt-out, which is exactly what the coverage score's +0.10 charging bonus and
`skills/02`'s opt-out rules already model. So it was measured before it was believed.**

`festival_crowd`, seed 42, 60 nodes, 100 messages at 1 s intervals, identical traffic plan
in every arm (§7's rule: an A/B that draws fresh traffic per arm is two experiments). The
tablets are the most open positions in the crowd — a café on a corner, not a phone in a
pocket.

| arm | delivery | relay tx | SUPER ratio | tablets elected | tx by *other* nodes | tx by tablets | NORMAL %/h |
|---|---|---|---|---|---|---|---|
| none | 0.910 | 23,518 | 15.0% | — | 23,518 | 0 | 2.914 |
| 3 tablets | 0.910 | 26,540 (+12.8%) | 20.0% | **3 of 3** | 23,414 (−0.4%) | 3,126 | 2.822 |
| 6 tablets | **0.980** | 24,444 | 21.7% | **4 of 6** | **19,148** (−18.6%) | 5,296 | 2.877 |
| flood-all baseline, either | 1.000 | ~205,000 | — | — | — | — | — |

*Measured after the two store-carry-forward fixes in §20.1, which moved every row: with
bundles actually being carried, six plugged SUPERs deliver seven more messages out of a
hundred instead of two fewer. The earlier version of this table showed the programme as
net-negative at three devices and only mildly positive at six; that was a measurement of
a broken DTN layer, and it is recorded in §20.4 as the reason a lever measured against a
broken baseline is not a lever.*

### 19.1 Three readings

**1. The election half works, immediately.** Every plugged, stationary, well-placed tablet
is elected SUPER in the first two cycles at three devices. That much of the roadmap line is
true and needs no qualification: the +0.10 charging bonus plus the peer count these
positions already have is decisive (§18 explains why the position alone would not be). What
the cap does is refuse two of the six, which turns out to be the interesting part.

**2. At three tablets the programme is close to neutral.** A SUPER relays everything by
design (roadmap Phase 2 item 65), so total relay traffic rises 12.8%; transmissions by
**other** nodes are flat (−0.4%), delivery does not move, and NORMAL drain falls 3.2%. Three
tablets buy a small battery dividend and nothing else.

**3. At six the programme starts to pay.** Delivery rises to **0.980** from 0.910, other
nodes' transmissions fall **18.6%**, and total relay traffic is *below* baseline. The reason
six works and three does not is the top-20% cap: at six the tablets displace battery-powered
SUPERs instead of joining them, so the mesh's relay work moves onto plugged devices. The cap
still elects only **four of the six** — a plugged tablet competes with the nodes the score
already favours — and the four that get in are enough.

Naive flood-all reaches 1.000 in both arms for roughly nine times the transmissions, so the
programme is not a substitute for reach; it is a way of buying the last seven points with
somebody else's power budget.

### 19.2 What the roadmap line should say instead

The claim it can support is real and larger than expected: **six plugged tablets in a
60-node crowd take 18.6% of the radio work off everybody else, lift delivery from 0.910 to
0.980, and lower NORMAL drain from 2.914 to 2.877 %/h** — because they displace
battery-powered routers instead of adding to them. Three tablets buy only the battery
dividend (2.914 → 2.822 %/h). The difference between three and six is the top-20% cap, so
the programme's unit is a quota, not a device.

Two consequences for whoever builds it:

* **Promotion has to be cap-aware.** Adding a community SUPER on top of an already-full
  elected set is the expensive case (three tablets: +9.2% work for everybody else). The
  useful version displaces a battery-powered SUPER, which means the election needs to know
  a candidate is community-hosted *before* it counts the top 20%, not after — e.g. reserve
  part of the cap for charging, stationary nodes, or score them so that a tablet beats a
  phone at equal position. **Both variants have since been implemented and measured, and
  the proposal is wrong about the mechanism: §19.4.**
* **Six is not three.** The benefit is a function of how much of the elected set the
  programme occupies. A single tablet in a café is a role change with a small battery
  dividend; a programme is a quota.

### 19.3 Scope of the claim

Measured in the TypeScript reference engine (`community relays` in
`src/__tests__/simulation.test.ts`), one seed, one world, `festival_crowd` — the case where
the idea has the most to gain, because a crowd is where battery-powered SUPERs are most
likely to be moving and drained. The delivery differences are one to seven messages out of a
hundred on a single seed, which is inside the band §16.4 warns about, and the ordering
*between* the three- and six-tablet arms on battery drain (2.822 against 2.877 %/h) is two
hundredths of a percent and is reported rather than asserted. A six-seed run is the next step
if this item is ever prioritised, and the harness above is what would run it. §19.4 ran the
cap-aware variants on three seeds (42, 7, 1234) with the same harness and 60 messages rather
than 100, so its numbers are comparable to each other and not to the single-seed table above.

### 19.4 Cap-aware promotion, implemented and rejected

§19.2 asked for the election to know a candidate is community-hosted before it counts the
top 20%. `communityRelayQuota` now does exactly that, in both forms proposed, and neither
form does what the proposal expected. A quota between 0 and 1 reserves that share of the
cap for community relays; a quota of 1 or more exempts them from the cap entirely (they
still have to clear the 0.60 score gate and the 30 m proximity guard). It ships at **0**,
inert, and the reason is below.

**The diagnosis first, because it decides everything.** Six plugged tablets in the
60-node crowd, seed 42, four elected. For each of the two that stayed NORMAL, the
candidates that outscored it were:

| blocked tablet | reason | better-scoring tablets | better-scoring phones |
|---|---|---|---|
| `node-1` | `NORMAL: score 0.77, rank 7/24` | **6** | 0 |
| `node-24` | `NORMAL: score 0.78, rank 6/23` | **5** | 0 |

The same holds on every seed measured: at seed 7 the two blocked tablets read `Backed off:
SUPER node-14 closer and better scored` — node-14 is another tablet — and at seed 1234 the
one blocked tablet faced five better tablets and one better phone. **A community relay that
fails to be elected is losing to other community relays, not to phones.** Reserving part of
the cap for community relays therefore cannot help them: the slots are already theirs, and
the weakest two tablets are competing against the strongest four. At three tablets the one
that sometimes loses is stopped by the proximity guard, which is docs/03 §5 working as
written — two plugged nodes in the same café should not both be routers.

**What the two variants do instead.** Mean of three seeds (42, 7, 1234), `festival_crowd`,
60 messages at 1 s, `relayPolicy: "mpr"`:

| tablets | quota | delivery | relay tx | SUPER ratio | elected | tx by others | tx by tablets | NORMAL %/h |
|---|---|---|---|---|---|---|---|---|
| 0 | — | 0.9333 | 10,565 | 19.4% | — | 10,565 | 0 | 2.873 |
| 3 | 0 | 0.9389 | 13,152 | 17.8% | 2.7/3 | 11,595 | 1,557 | 2.803 |
| 3 | 0.5 | **0.9556** | **11,721** | 20.0% | 2.7/3 | **10,381** | 1,341 | 2.846 |
| 3 | 1 | 0.9389 | 13,152 | 17.8% | 2.7/3 | 11,595 | 1,557 | 2.803 |
| 6 | 0 | 0.9444 | 12,063 | 18.3% | 4.7/6 | **9,418** | 2,645 | 2.775 |
| 6 | 0.5 | 0.9111 | 11,872 | 21.1% | 4.7/6 | 9,334 | 2,538 | 2.795 |
| 6 | 1 | **0.9611** | 13,309 | 18.9% | **5.3/6** | 10,573 | 2,735 | **2.732** |

* **Quota 1 is byte-identical to quota 0 at three tablets**, and at six it elects all of
  them on seed 42 (4/6 → 6/6) and lifts delivery 1.7 points — while pushing the SUPER ratio
  to 15/60 = **25.0%**, exactly the ceiling of skills/02's band, and raising everybody
  else's transmissions from 9,418 to 10,573 (+12%), back to the no-tablet baseline. The
  programme's whole claim is moving relay work *off* other people's batteries, and the
  exemption moves it back on.
* **Quota 0.5 does not reserve anything for tablets.** A tablet already outscores every
  phone in range, so those slots were already theirs; taking them out of the open pool
  *loosens* the rule for phones, and on seed 42 at three tablets the elected set gains one
  member that is a phone (13 → 14 SUPERs, tablets unchanged at 3/3). The improvement it
  shows at three tablets (delivery 0.9389 → 0.9556, other people's transmissions 11,595 →
  10,381, below the no-tablet baseline) is real on three seeds and worth following up, but
  it is an accident of a looser cap rather than the displacement that was asked for — and
  at six tablets the same knob costs 3.3 points of delivery.
* **Neither variant is a quota.** A quota moves work from phones to tablets at a fixed
  number of routers. What both variants actually do is change *how many* routers there are,
  which is the variable skills/02 already constrains.

**Verdict:** implemented, default 0, documented as rejected. The lever §19.2 named is aimed
at a mechanism that is not operating. If the roadmap's community-relay programme is ever
prioritised, the useful question is not how to elect more tablets — six plugged nodes in one
crowd get four elected and the other two are correctly redundant — but whether a tablet
should be *preferred* as an MPR and as a bundle carrier, where the work actually is.

## 20. Store-carry-forward: two defects, one rejected lever, one rule that never fires

**`skills/04` specifies the DTN layer in four rules and three acceptance boxes. The queue,
the cap, the seven-day expiry and the spray limit were all implemented as written; the first
acceptance box — "A→C: A enqueues for C (C offline); B meets A then later C → C receives" —
did not pass. Writing the test found two independent reasons, and fixing them moved the
crowd's delivery ratio by eight points.**

### 20.1 Two defects, and what fixing them was worth

**(a) Sprayed copies reused the source retries' attempt numbers.** A bundle is parked after
the originator's two retries, which have already used `attempt` 1 and 2. The spray then
numbered its copies from 1, and since intermediate nodes dedupe on `id#attempt` (exactly so
that a source retry is not swallowed by nodes that already relayed attempt 0), the first two
of three copies were thrown away by every relay that had heard the retries. The bundle's
whole spray budget was spent on copies nobody forwarded. *Fix:* increment relative to the
attempt the bundle is already on.

**(b) A carried bundle with no route was deleted by flood suppression.** With the destination
offline, a carrier's route lookup fails, the copy falls through to the flood branch, and a
NORMAL node suppresses it — the log reads `MPR: heard relays cover all my neighbours`, where
the "relays" it heard were the originator's own transmissions. MPR suppression exists to
delete duplicate copies of a *flood*; a bundle that has nowhere to go right now is not a
duplicate, it is the message. *Fix:* a message already marked `carried` is parked, never
flooded and never suppressed.

Measured over six seeds per world, 100 messages on an identical traffic plan per arm:

| world | delivery before | after | DTN deliveries per run | parked at end | routed p95 |
|---|---|---|---|---|---|
| campus_quad | 0.9933 | 0.9967 | 0.2 → 0 | 1.5 | 2.3 s |
| sparse_village | 0.2783 | 0.2783 | 0 | 67.3 | 0.3 s |
| **festival_crowd** | 0.8667 | **0.9467** | 0.5 → **5.0** | 39.3 | 6.6 s |
| partitioned_pair | 0.4483 | 0.4483 | 0 | 50.8 | 1.0 s |

The crowd is where it shows: **+8.0 delivery points**, and five messages in a hundred now
arrive by store-carry-forward that previously did not arrive at all. The two sparse and
partitioned worlds do not move, because there the destination has no chain of links to the
sender (§11) and carrying cannot substitute for topology.

Note the two p95 columns' worth of difference in the crowd: **6.6 s over routed deliveries
against 17.8 s over all of them**. That gap is the `carried` flag doing its job — keeping
opportunistic deliveries out of the latency budget `docs/04` §5 writes for routed traffic —
and this is the measurement that shows why the separation has to exist rather than being a
bookkeeping preference.

The golden vectors did not move: the fixture parks no bundles (`totalQueued: 0`), so a run
that never carries anything cannot be affected by how carrying works.

### 20.2 The other two acceptance boxes

* **Spray limit** — asserted end-to-end from the capture log rather than from queue state:
  the number of transmissions of one bundle's id by nodes other than its originator is
  ≤ `SPRAY_LIMIT`. The queue-level version of this test already existed; the network-level
  one is what the criterion actually says ("same msg not duplicated >3× in network capture").
* **Expiry** — seven days of simulated time is 2.4 M physics ticks, which is not runnable
  event by event, so the boundary is asserted on the sweeper: a bundle survives at exactly
  `OPP_TTL_MS` and is gone at `OPP_TTL_MS + 1`. Stated here because it is the one box that
  is verified by construction rather than by running the clock.

### 20.3 "Keep newest 500 (LRU by priority)"

The cap evicted the *oldest* bundle whatever its priority, which could throw away a fresh
bundle to keep one that had already sprayed its three copies and been demoted to low. Now
priority ranks first and age second, and a test fills the queue to 500 with a mix and asserts
that both demoted bundles go before any normal one.

### 20.4 A lever the fixes made unnecessary: preferring SUPER as bundle carrier

`skills/04` says *"DO prefer SUPER as bundle carrier (more storage/battery)"*. Implemented
as: when the carrier has no route of its own, hand the bundle to the strongest SUPER in
range, still bounded by the spray limit.

* **Measured before the §20.1 fixes:** crowd delivery 0.867 → 0.912 (**+4.5 points**) for
  +9.9% relay traffic. It looked like a clear win — because a SUPER relays everything, so
  handing bundles to SUPERs rescued them from the suppression that was deleting them.
* **Measured after the fixes:** crowd delivery 0.947 → **0.912** (**−3.5 points**), DTN
  deliveries 5.0 → 2.0, parked bundles 39.3 → 62.5, at 155 SUPER carries per run. In the two
  partitioned worlds delivery is unchanged and parked bundles grow (67.3 → 97.2 and
  50.8 → 90.0) for ~10% more relay traffic.

So the lever is **off by default** (`dtnPreferSuper: false`) and stays in the code so the
measurement can be repeated. The reading: the rule's intuition is about who should *hold* a
bundle — a plugged, roomy device — not about who should be *handed extra copies*. Spraying
toward SUPERs duplicates work into the queues of the busiest nodes in the network. If the
product wants community relays to carry bundles, the lever to build is a storage- and
battery-aware **eviction** preference, not a spray preference; §19 measures what community
relays do to the rest of the mesh once they are elected.

The ordering matters more than the numbers: **this lever was measured as a win, then the two
defects were fixed, then it became a loss.** A lever measured against a broken baseline is
not a lever, and the same trap sits in front of anybody who re-runs this experiment on an
engine that has not had §20.1 applied.

### 20.5 "Gossip ACK so relays can prune" prunes nothing

Implemented as specified: a bundle delivered by store-carry-forward is acknowledged to the
carrier that handed it over rather than to the originator (whose retry timer expired long
ago), and any node that hears an ACK for a bundle id drops its copy — no new packet type and
no extra traffic, because the ACK travels the reverse path anyway.

Measured over six seeds and four worlds: **zero bundles pruned.** The carrier that delivered
has already dropped its own copy on delivery, and other holders are pruned only if they
happen to relay that particular ACK, which in these worlds they never do. The originator's
copy waits out the seven-day TTL.

Two options, neither taken: re-flood the prune (in the crowd that is ~5 broadcasts per 100
messages — cheap, but it is a flood for a housekeeping message), or accept that the cap is
managed by TTL and LRU alone. The cap never binds in any world measured here (at most 97 of
500 slots), so the honest position is: keep the free unicast prune, do not add a prune flood
until a deployment shows cap pressure, and record in the skill that the rule as written does
not do what it sounds like.

### 20.6 Accounting

Two new counters, `bundlesPruned` and `dtnSuperCarries`, so both of the above can be checked
without re-deriving them from logs. Queue events are attributed per node, and a test asserts
that the originator's own queue matches its own queue events — which is how the
multi-carrier case became visible in the first place.
